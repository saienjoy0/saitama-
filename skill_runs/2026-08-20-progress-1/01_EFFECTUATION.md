# Effectuation — rerun with 今の進捗(1)

Applied upstream skill: `thinking-effectuation`.

## means
- A much clearer non-negotiable purpose: transfer noticing, interpretation, proposal and decision-making toward the child.
- Concrete lightweight implementation hypotheses: AI apprentice, support profile, hint ladder, fading entry screen.
- A manual/concierge path that can test these without a full app.
- Parent role and burden constraints are now explicit.
- A measurable success direction: support should reduce where the child becomes capable.

## affordable_loss
Until the core interaction is proven:
- no full production app;
- no complex child profile engine;
- no payment infrastructure;
- no grandparent-heavy flow;
- no persistent family newspaper system;
- minimal child/family data;
- small invited household tests.

## next_action
Run a repeated manual household test that measures not only first-session enjoyment but **support decay**.

For each child, record per attempt:
1. what situation was presented;
2. where the child got stuck (notice / articulate / solve / negotiate / reflect);
3. which hint-ladder step was needed;
4. whether the same support was needed next time;
5. whether the child later brought in a situation without a prompt.

## commitments sought
- Child voluntarily asks for / starts another attempt.
- Parent supplies a second real situation without being chased.
- Parent tolerates genuine child refusal/modification.
- Child later returns with a self-noticed situation.
- Parent accepts a concrete paid continuation after experiencing value.

## contingencies
- If AI-apprentice framing is fun but support never fades, keep the fun wrapper but redesign the mechanism.
- If support profile is too complex to infer reliably, replace it with simple per-session hint history.
- If parent input creates burden, reduce parent role to a one-tap situation seed or post-action feedback only.
- If fading prompts reduce engagement before self-initiation appears, slow the fade rather than treating usage decline as success automatically.

## emerging goal
Find a repeatable interaction where the child both **wants to return** and **needs less externally supplied structure over time**, while the parent experiences enough value with low enough burden to continue and eventually pay.

## stop_or_loop
Do not switch to build mode merely because first-use reactions are positive. Switch only when there is evidence of repeat behavior plus at least an early signal of scaffolding reduction and parent commitment.
