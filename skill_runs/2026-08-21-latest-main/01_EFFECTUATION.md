# Effectuation Brief — Latest Main Spec

Applied skill: `thinking-effectuation`

## means

### Identity / assets actually present in the project
- A clearly stated non-negotiable purpose: transfer problem-discovery and decision-making agency to the child.
- A detailed current interaction loop and explicit boundaries around compensation, family feedback, AI, grandparents, safety, and reflection.
- A concrete but falsifiable onboarding hypothesis (`AI apprentice + household exploration`).
- A concrete support-fading design family: support profile, hint ladder, fading onboarding prompts.
- New competitive evidence that invalidated an earlier simplistic differentiation claim, showing the project can update rather than defend sunk assumptions.
- A research-backed design vocabulary (contingency / fading / transfer of responsibility) used with an explicit evidence caveat.
- A PoC definition already oriented toward observable behavior, not feature count.

### What remains unavailable / uncertain
- No validated initial age segment.
- No validated parent problem intensity/frequency.
- No validated payer or price.
- No behavioral evidence yet that total support actually declines or transfers across situations.
- No validated business model for the possibility that successful users eventually need less product support.

## affordable_loss

The latest spec does not set founder-approved numeric caps for time, money, or reputation. Therefore no hard cap should be invented.

Proposed non-numeric cap for the next cycle:
- no full application build before the transfer mechanism is behaviorally tested;
- no large acquisition spend before the parent problem and repeat behavior are shown;
- no collection of unnecessary child/family data;
- no claim of long-term autonomy improvement from a 3–5 session test;
- no commercial architecture built around “maximum usage” until the reduced-usage-success tension is understood.

## next_action

Run **one longitudinal concierge cycle with the same child-parent pair for 3–5 sessions**.

For each core step (notice / frame / solution / negotiate / propose / reflect), record:
- whether the child initiated independently;
- maximum AI support intensity needed;
- parent/family interventions that supplied hints or answers;
- whether the child chose to return;
- whether a new situation was child-brought rather than prompted.

This is more discriminating than building new features because it can falsify the central transfer-of-control mechanism.

## commitments_sought_or_won

Seek commitments, not praise:

1. Parent commits a real household situation and actual time for the first session.
2. Household returns for session 2 without researcher pressure.
3. Same household completes enough repeated sessions to observe support-fading signals.
4. Parent allows genuine safe refusal/modification instead of forcing task completion.
5. After value is experienced, parent accepts or rejects a concrete paid-continuation offer.
6. Strong parent may introduce another household, staking reputation.

## contingencies_used

A useful contingency has already occurred: competitor research weakened “problem discovery itself is the differentiator.”

Use that surprise as a new means. The emerging bet is narrower and more testable: **support should adapt, fade, and transfer responsibility**.

If AI-apprentice engagement is weak but the transfer mechanism works with simpler cards/prompts, remove AI from the foreground.
If children enjoy AI but support does not decline, treat that as failure of the core mechanism, not a retention win.
If support declines but children dislike returning, redesign experience rather than claiming educational success.
If parents are the dominant source of answers, the product must redesign parent involvement before adding child-facing sophistication.

## emerging_goal

> Find a repeatable household interaction that children voluntarily re-enter, where the total support required to notice/frame/solve a new situation falls over time and responsibility visibly moves toward the child — then identify the adult who will repeatedly commit time and money to enabling that process.

## stop_or_loop

Continue effectuation while user/payer/mechanism uncertainty remains high.

Switch toward conventional execution only after:
- a usable initial segment is identified;
- the repeat + fading + spontaneous-transfer signal appears in repeated behavior;
- parent burden is acceptable;
- a payer makes real commitment.

Halt or pivot the implementation if repeated cheap tests show that support cannot fade without killing engagement or causing adults to take over.
