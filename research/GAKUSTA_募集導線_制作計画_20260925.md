# Googleフォーム・紹介・LPの制作計画 v1

> 制作担当：ChatGPT/Codex。native/sequentialを提案。制作時はsuperpowers:executing-plansを用い、順番に進める。今回は計画作成であり、各制作物は未実装。

**Goal:** 保護者が紹介やXから募集内容を理解し、フォームへ応募して、本人との面談へ進める状態を作る。

**Architecture:** 1枚の募集LPからGoogleフォームへ移動。紹介文から同じフォームへ直行も可能。個人情報は本人のGoogleアカウントで管理し、公開サイトに保存しない。

**Tech Stack:** 静的HTML/CSS、Google Forms、必要時Google Apps Script、非公開Google Sheets。公開先は制作時にSites等の利用可否を確認する。

**Spec:** [募集導線の設計](GAKUSTA_募集導線_Googleフォーム・紹介・LP_設計_20260925.md)。先に読む。

## 共通条件

- 発表はユーザー指定10/16。まず1週間で5家庭、10/12までを目安に10家庭。日本時間で案内する。
- 面談は保護者のみ20〜30分。フォーム約3分は設計目標。
- 謝礼1,000円、上限15,000円は提案であり、支出承認・実行済みではない。
- 実回答・連絡先・認証情報・編集URLを公開GitHubへ置かない。
- Googleフォームの直接作成連携は現環境で見つかっていない。接続がなければ私が生成スクリプトを用意し、本人のGoogleアカウントで実行・認可する。
- LPは単独の募集ページ。製品本体のUI/API/DBを変更しない。製品のD90と募集導線の制作指示は別対象として記録する。
- 公開・送信・契約・支払いは実行した事実と指示の範囲を記録する。今回の計画依頼では行わない。
- 合成入力の結果を実際の調査実績に含めない。

## 特に確認する5つの失敗

1. Googleログイン・組織制限で応募できない：Task 2でログアウト確認。
2. 対象外・日時未定・満足する人の誤処理：Task 2でR-A03〜07。
3. 他人の回答・メールアドレスが見える：Task 2でR-A09。
4. LPとフォームで謝礼・時間・URLが違う：Task 3〜4でR-A12。
5. 送信を予約確定と表示し、夫婦を2家庭と数える：Task 1と4でR-A08。

## Task 1：文面と空の運用資料

**依存:** 設計書。アカウント接続不要。
**入力:** 設計書第3〜9節。
**出力:** form-spec、recruitment-copy、空テンプレート、release-checklist。

- [ ] Q1〜Q9と対象外分岐、全経路で矛盾しない送信後文面を実フォーム用に整理する。
- [ ] 紹介依頼、転送、X、日程提案、日程確定、辞退受付を別の文面にする。
- [ ] 管理表の列を「家庭ID／経路／本人との関係／主枠／状態／日時JST／謝礼条件／謝礼状態／記録参照」とする。
- [ ] メールアドレスは別の非公開連絡簿で家庭IDへひも付ける運用を記す。
- [ ] 面談記録を「質問版／回答者／直近の一件／現在の対応／不足または十分な理由／時間・費用／反証／解釈／変更案／未確認」にする。
- [ ] 対象外、無返信、予約未確定、夫婦2名の合成ケースで状態と家庭数の扱いを確認する。

**完了:** 文面と管理状態が一致し、実連絡先と実回答を含まない。

## Task 2：Googleフォームの生成と実環境確認

**依存:** Task 1。
**入力:** 設問、本人のGoogleアカウント、公開メール、面談可能枠、確定した謝礼。
**出力:** 非公開フォーム、非公開回答先、確認済み回答用URL。未接続なら生成用ファイルまでを完了とする。

- [ ] 制作時に認証済み操作手段があるか確認する。なければ私がFormAppの生成スクリプトを書く。
- [ ] 公開メール・日時・謝礼の必須設定が未入力なら説明付きで停止し、公開可能と表示しない。
- [ ] FormApp.create(title, false)で非公開作成する。自動公開、招待、メール送信を含めない。
- [ ] 作成IDを本人のScript Propertiesへ保存する。再実行時は既存フォームの編集先を返し、増殖・実回答の消去を避ける。
- [ ] 設問・分岐・メール形式・必須と任意・確認文を実装する。回答シートは所有者のみ共有とする。
- [ ] 本人のアカウントで認可・実行し結果を確認する。アクセスできない場合は実行を未確認と記録する。
- [ ] 本人がテスト受付を許可した段階で回答可能にし、ログアウト環境とスマホでR-A02〜R-A09を試す。
- [ ] 合成回答を確認後に削除し、本番募集前の件数を確認する。検証結果に個人情報を残さない。

**完了:** スクリプト作成とGoogle上での生成・回答可否を別々に報告できる。

## Task 3：LPプレビュー

**依存:** Task 1。フォーム未生成でも制作可能。
**入力:** 設計書第4節の原稿。
**出力:** index.html、styles.cssと確認用プレビュー。

- [ ] 制作時はSites等、実際に使う制作手段のスキルを読む。既存サイトを使う場合は変更先を先に確認する。
- [ ] 見出し、条件、主ボタン、説明、実施者、FAQ、取扱い、主ボタン再掲の順で作る。
- [ ] 主行動は「インタビューに応募する（約3分）」だけにする。回答URL未取得は「募集準備中」とし、ボタンを無効にする。
- [ ] 360px・390px・PC、文字200%拡大、キーボードで確認する。R-A01、R-A10、R-A11を記録する。
- [ ] 入力DB・AI・広告計測は追加しない。閲覧数は未計測とする。
- [ ] 公開済みと誤認しない形でプレビューを提示する。

**完了:** 見た目をレビューでき、未接続なら明示される。静的文章だけの変更に実装をなぞる自動テストを増やさない。

## Task 4：接続と公開用一式の仕上げ

**依存:** 実フォームとLP。
**入力:** 回答用URL、公開メール、面談枠、謝礼、公開先。
**出力:** 実URL入りLP・募集原稿・確認結果。

- [ ] 編集用でなく回答用URLを接続する。フォーム直行でも説明が不足しないことを確認する。
- [ ] LP→フォーム→送信後→日程連絡草案を通してR-A08、R-A12を確認する。
- [ ] LINE/X内ブラウザも確認可能な範囲で試す。試せなかった環境を合格扱いにしない。
- [ ] アカウント、公開メール、面談枠、謝礼、公開先、回答URLと募集期限の一致を確認する。
- [ ] 公開する具体物を提示する。公開依頼がある場合にフォームとLPを受付可能な状態へ揃え、公開後のリンクを確認する。
- [ ] 通知・DM・投稿は送信の明示的指示がある場合だけ行う。
- [ ] 締切・満席時はフォームの受付停止とLPの募集終了表示を揃える手順を残す。自動化していなければ自動とは言わない。

**完了:** R-A01〜R-A12の実結果と未確認、公開状態と送信状態を区別できる。

## Task 5：募集後の判断と発表

**依存:** 実際の募集開始。制作完了と別の活動。

- [ ] 本人が紹介候補10人程度を選び、依頼を送る。
- [ ] 48時間後に応募と予約確定を分けて確認。5枠に不足なら、欠けた対象への紹介・X募集を追加する。
- [ ] 有料募集が必要なら本人が発注条件を決める。CrowdWorksの応募者を先に外部フォームへ誘導しない。
- [ ] 面談ごとに記録。5家庭時点で支持・反証・対象の偏りを整理する。
- [ ] 10/12までを目安に追加面談し、未達なら実数を示す。
- [ ] 10/13〜15に「仮説→実施方法→事実と反証→変更→次の確認」を1〜2枚にまとめる。

**完了:** 件数だけでなく、どの事実から何を変えたか示せる。制作完了を需要検証完了にしない。
