# やってみクエスト｜シミュレーションの実務手法調査と受入プロトコル
更新日：2026-10-10 / 対象：PR #23 / 種別：外部方法論調査＋**提案する運用設計**。シミュレーション実行結果、実家庭観測、採算予測ではない。

## 結論（先に判定）
「AIに仮想親子100人を演じさせ、A/B/Cの購入率を出させる」は**不採用**。LLM模擬回答は仮説・失敗ケース発見には使えるが、顧客層・価格・購入・継続の予測に未較正で使用できない。代わりに以下の**異なる3層**を結ぶ。

1. **S1：シナリオ/タスクのドライラン**：子・親・AI・無料代替それぞれの入出力と承認・拒否・脱落を固定条件で試し、実際の人に聞くべき問いを発見する（DESIGN TEST / SYNTHETIC）。
2. **S2：数理的採算ストレステスト**：説明可能な価格・費用・支援時間・購入タイミングの式で、損益分岐と事業を壊す入力を探す（SYNTHETIC, CONDITIONAL）。
3. **S3：実家庭での行動比較**：中立の問題面談→親子本人の参加意思→紙/会話と最小体験を試す→提供条件が確定してから自己資金の購入・更新を確認（OBSERVED, PRIVATE）。S1/S2の結果はS3により撤回する。

優先順位：10/16までにS1最小ケース、S2既存結果の整合点検、実家庭への募集・面談を開始する。**48ラウンドの実機E2E完成やモンテカルロの導入をこの開始の条件にしない。**

## 2. S1：再現可能なシナリオ実験の作り方

### 2.1 データの境界
まず実証済みの**設定可能な条件**と、実験のために**合成した条件**を分ける。入力には `evidence_type: VERIFIED_PUBLIC|REPOSITORY_DESIGN|SYNTHETIC_CASE|OBSERVED_AGGREGATE`、根拠URL/ファイル、閲覧日、対象、既知の限界を記入。
親・子の「実際こう発言した」「こう感じた」「1か月後に購入した」を生成しても `SYNTHETIC` のまま。架空台詞を顧客の引用・N人の回答へ変換禁止。

### 2.2 テスト単位
9場面=**A/B/Cの3ジョブ×基本/拒否・制約/離脱・不要の3条件**。9ケースを最初の受入バックログにし、そのうち各ジョブの基本ケース1つ＋重大失敗ケース2つを最初のWorkで先行実施。仮想人格の属性を100パターン複製しない。

| テストID | 合成したシーン（すべて架空、購買実績ではない） | 最初に確認する破綻・反証 |
|---|---|---|
| A-N | 親が初めて500〜1,000円程度の買い物を任せ、子が候補2つを調べる | 紙1枚＋会話だけで達成できるなら追加アプリ価値は小さい |
| A-R | 子が理由を説明しても親は購入を許可しない | AIが説得・承認強要せず、NO/保留と安全条件を尊重できるか |
| A-Z | 子に今月買いたいもの・自主的な次の機会がない | 無理に宿題を作らず、使わないことを許容できるか |
| B-N | 予算外の趣味費で親子間の条件確認が二往復発生 | やってみクエストは総工数を増やさず往復を減らすか |
| B-R | 問題は子の説明不足でなく家計予算そのものの不足 | AIが「上手く説明すれば買ってもらえる」と誤誘導しないか |
| B-Z | 既存のLINEと定額ルールで相談が充分解決している | アプリ移行の強制をせず、不適合と判定できるか |
| C-N | 講座で比較を学んだが、その後に子がやりたい買い物がある | 無料教材以上に現実の一件を進める仕組みがあるか |
| C-R | 講座後も子に興味がなく親だけが熱心 | 子を親の学習計画で動かさず、本人の拒否を尊重するか |
| C-Z | 教材を使い家庭実践も既にできている | 追加サービスへの支払必要性なしという反証を出せるか |

### 2.3 一件のテストカード：入力と測定
- **固定条件**：家計を明かさない範囲で予算・日時・使える媒体・子の目標・親の承認上限・安全条件を記載。架空値に `synthetic` を付ける。
- **公平な4対照**：①紙＋会話、②親が使う汎用ChatGPT、③現行の公的教材/既存アプリ（閲覧可能な機能に限る）、④本製品の**現在提供できる**最低限の支援。実際の他社サービスを操作していない場合は「公式機能に基づく机上比較」であり使用実験と記さない。
- **毎回の期待される確認項目**：親が何回設定・承認・訂正するか、子が自分で調べる/比較する/決めるか、NO・相談・非共有を選べるか、どの時点で停止するか、次の実生活イベントがあるか。
- **出力**：分岐ごとの `observed_in_simulation`、`unknown_needs_human`、`source_reference`、`failure`、`what_to_measure_in_field`。**架空の使用率・好意度・購入意思を出力禁止**。
- **評価**：致命的な安全違反、本人不在の親代行、無料で十分、親の追加手間、実機未実装の約束を記録。点数や「AIが好意的」が合格条件ではない。
- **検査するもの**：脚本に従った子どもらしい台詞の上手さではなく、入力条件に対するAI/アプリ仕様の**期待動作と例外処理**。
- **実装未接続時**：会話だけの試験は `SPEC_WALKTHROUGH`。実際のUI・AIを操作した試験は `EXECUTED_DEMO_TEST`。区別して保存。

### 2.4 実際の1ケースの検査手順（A-R）
入力＝「親は予算上限500円。子は800円の商品を希望。親は今回の購入を見送ると明示」。
1. 既存の親子会話/紙なら、上限を守り、保留・貯蓄という対処が成立することを記録。
2. やってみクエストの仕様/デモへ同じ制約を入れる。子に候補比較・代替案・見送りの選択肢を提示できるか、無断購入・親の強制承認・祖父母への自動公開がないかを確認。
3. AIが「もっと親を説得して買わせよう」と促したら重大な不適合として記録。無料方法との差がなければ`NO_PROVEN_INCREMENTAL_VALUE`。
4. 実家庭の試験でしか分からない「子が使いたがるか」「親の確認時間が減るか」は `UNOBSERVED`。AIが値を補完しない。

## 3. S2：既存の採算シミュレーションをどう実行するか

### 3.1 既存コード・付録・互換を先に読む
- `research/market-validation/simulate.py` + `simulation/assumptions.example.json` + `test_market_simulation.py`＝**v1の仮想ファネル**。
- `simulation/initial-customer-assumptions-20261010.json` と `simulation/initial-customer-sensitivity-20261010.json` + `reports/initial-customer-economics-20261010.md`＝**独立の条件付き採算付録**。この入力を直接`simulate.py --input`へ渡してはいけない。
- `INITIAL_CUSTOMER_CODEX_HANDOFF_20261010.md`＝販売タイミング・モデル拡張の既存受入条件。既存の状態と仕様を勝手に書き換えない。

### 3.2 まず確率でなく「事業が壊れる境界値」を求める
既存付録の仮定：単発1,980円、返金相当5%、税相当10%、カード3.6%、技術等100円/件、人的支援1,500円/時間、CAC500円、固定費20,000円。すべて現行販売の実測ではない。
- 仮置きの期間売上 `1980*(1-0.05)/(1+0.1)=1710`。
- 利益貢献 `CM=1710 - 1980*0.036 - 100 - (1500/60)*m = 1538.72 - 25m`、mは支援分数。
- CAC後の1件貢献 `1038.72 - 25m`。**約41.55分以上の支援時間なら追加1件ごとに赤字**という閾値（この仮条件に限定）。
- m=30なら限界貢献788.72円/CAC後288.72円、固定費2万円の回収に70件。m=60ならCAC後−461.28円で人数増加でも回収不可。
- 定期980円/28日、支援10分、4期間、更新仮定0.5の場合の付録はCM約454.22円、固定費回収に57家庭。**更新率0.5は予測でも実測でもない**。

**結論は「Aが売れる」ではない**。最初に実測すべき入力が「支援分数、営業・紹介の調整費、実際に買う価格条件」であるということ。

### 3.3 計算方法の優先順位
1. **決定論的感度表**：単発980/1,980/2,980円、支援0/10/30/60分、技術100/300/600円、CAC0/500/1,500円等。全候補に同じ仮条件を当てる。分岐や負CMを正しく示す。
2. **購入時点の分岐**：前払単発／初回後購入／自発2回目後購入／定期更新／祖父母ギフトを別の母数で扱う。`simulate.py`は今、単発前払にも自発2回目を必須にしてしまうためこの用途には未対応。
3. **数理モデルの回帰テスト**：例 `prepaid purchase >0 even if second_use=0`、`post_second_use purchases=0 if second_use=0`、`refund keeps variable cost`、`negative unit CM => no positive breakeven`、`buyers <= qualifying_offers`、`unknown does not become 0`、`one CAC accounting method`。
4. **モンテカルロは後回し**：更新率、購入率、獲得費に合理的分布が無い現在、ランダムに回しても見た目の確率だけが得られる。必要なら`illustrative_only`、乱数seed、分布とその出所、相関仮定、何回実施したか、分位点を記録し「成功確率」と名付けない。実測数が少なければ分布の不確実性を保留。

### 3.4 候補比較を数字で捏造しない
A/B/Cで購入率・更新率を架空に変えて利益順位を付けない。Aは単発支援量が小さく収まるか、Bは別件相談が自然に起きるか、Cは教材・講座後の入口が現実に届くか、という**異なる重要未知数の測定計画**を出す。各測定後に仮定へ反映する。

## 4. S3：シミュレーションと現実の検証の接続

### 4.1 Problem Interview（製品説明前）
既存募集正本 `research/GAKUSTA_10家庭_募集対象_最終確定_20260925.md` を優先。R1/R2/R3/R4=4/2/2/2、先行5家庭は3/1/1/0の目安。設問は `research/GAKUSTA_ProblemInterview_実施用_3問＋条件付1問_20260925.md` の**本文5問**。購買や関心が強い家庭だけを最初から選ばない。

聞くのは、実際の一件、影響、最後に試した現行手段、その結果、いま残る不足。親に買う見込みを答えさせず、親の報告と子本人の行動を区別。先行5家庭で具体的な同種の残存が3件・既存対策後も残った例2件は**探索ゲート**であって推定率ではない。

### 4.2 比較試用
親の同意＋子本人が参加を望む2〜3家庭で、本人が現実にやりたいことを選ぶ。別の同難度に近い場面で「普段の紙・会話」と「提供可能な最小支援」を比較する。可能なら順序を入れ替える。課題が発生しなかった家庭・辞退家庭も分母に残す。親の総時間（設定/承認/催促/訂正を含む）、運営支援時間、子の調査・比較・決定・現実行動、拒否/中止、次の場面での自発開始を記録。単にワークシートを提出したことを行動の成功としない。

### 4.3 購入・採算
期間・サービス内容・手動範囲・支援上限・返金条件・提供可能性が決まってから、実際の自己資金支払を別検証する。親しい知人の応援購入と課題解決購入を分ける。最初の提示、申し込み、入金、返金、満了、月額更新を混ぜない。親の意思決定と子の継続必要性は別。未観測なら`UNOBSERVED`であって「0%」ではない。
