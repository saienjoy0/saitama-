# Motion and change review

For every animation, specify its purpose, trigger, duration, distance, easing, reduced-motion behavior, and the persisted state it represents. Choose CSS for simple transitions before adding a new runtime. Never gate correctness on animationend.

- Child: make selection, progress, and saved discoveries understandable. Do not attach louder rewards to money, daily streaks, or compliance.
- Parent: make changed content, recipients, and review status clear. Avoid moving targets while approving.
- Grandparent: preserve reading position, large text, and stable controls. No simulated rotating pages, parallax, or automatic scrolling.
- Use OS reduced-motion OR the user's reduced-motion preference. Provide the same information statically. Keep a persistent textual status and announce updates once.
- Wait for a durable save/send acknowledgment before success motion. On failure preserve input and show unsent state. Reduced motion must not change request counts or approval requirements.
- Separate changeable content/theme/navigation tokens from immutable consent/tenant rules. Add a template by data, not by copying an entire screen. Test old content versions after changing the current template.

Review each feature against: what the role came to do, whether the next action is understandable, whether alternatives/skip exist, what happens without family participation, and what evidence would make the team remove or change it. Name the proposed scope and unsupported surfaces. Do not call a mockup user-validated.
