# 課題分解AIとCodex着手性の最小レビュー v0.4.1

2026-09-23／DESIGN、ユーザーの「大きな課題の細分化、既存事例、スキルの導入と適切さをレビューして最小修正」に対応。v0.4の画面・同意・提供元・運用上限を維持し、F18/B60に限定した設計差分。実装・モデル評価・利用者観察ではない。

## 判断

**製品の中核候補は「その子が判断できる小さな手順へ分け、必要な支援だけを出す機能」。外部LLMはその一部として比較する。** 独自モデルの学習、別AIサーバー群、自律エージェント、LangGraph等の追加は現在不要。FastAPI内の通常コードと既存provider adapterで始める。

v0.4のnext_action_matchは候補検索であり、課題分解や支援の調整を実現したとは言えない。これだけで差別化できるという説明は弱い。一方、万能なAIが全手順と答えを渡すと、本人の判断を育てる原案に逆行する。

| 案 | できること | 判断 |
|---|---|---|
| 固定の体験・手順 | 監修済みの題材を少ない負担で試す | D0/M1の通常動作・比較基準 |
| 制約付きの課題分解＋必要時のヒント | 本人の目的と「どこで困ったか」に応じて監修部品から手順案を組む | B60の追加比較対象、推奨する中核仮説 |
| 自律エージェントが目標達成を代行 | 調査・計画・実行をモデルが反復 | M1では不採用。本人の選択を代行し、費用・権限・検証範囲も増える |

既存サービスのコード・APIを取り込む提案ではない。**差別化仮説は「家庭の実際の判断＋本人の理由＋任意の家族経験＋別場面で支援を減らせるか」の組合せ。** 現時点では模倣困難性、教育効果、継続率、支払意思は未証明。蓄積件数の多さを価値にせず、同意した範囲の教材・評価例と実際の改善を資産にする。

## 具体例：『欲しいものにあと500円足りない』

最初の問いは「何が一番困っている？」。本人が「どう比べたらよいか」を選んだ場合、次の小さな判断を最大5個の手順案として示す。

1. 欲しい理由と、いつ必要かを自分で選ぶ。
2. 今使えるお金と不足を、架空の金額または自分が入力を選んだ範囲で確かめる。
3. 待つ／別の物／買わない等、少なくとも二つを比べる。
4. 自分で一つ選び、理由を残す。相談は選択肢であり、借金・仕事・報酬を自動提案しない。
5. 後で選択を振り返る。家族の経験を使うかは本人が選ぶ。

最初から全欄をAIが埋めない。子には「いまの一歩」と折りたためる全体像を表示。「もっと小さく」「自分でやる」「別のやり方」「やめる」を残す。C02の拡張であり、新しいチャット画面は作らない。親が全手順を監視・採点する導線にしない。

## 最小エンジンの契約（F18/B60）

### 固定コードとAIの分担

- `StepCatalog`：監修部品のid/version、目的、表示文、前提step、観察できる完了条件、利用条件、任意の小分け経路、段階別ヒント。最初は買い物・予算の1題材だけ。未監修の文章を子へ表示しない。
- `ScaffoldPolicy`：本人の操作 `need_smaller|need_hint|try_alone|pause` から支援表示を制御する通常コード。無回答・所要時間から能力や性格を推定しない。新しい体験のヒントは閉じて始め、いつでも戻せる。安全条件は減らさない。
- `GuidedPlanner`：本人の確認済み目的・困り所を、候補内のstep IDの順序へ対応付ける単発LLM呼出し。next_action_matchは「どの体験」、guided_planは「その体験をどの手順で進めるか」。同じ操作で二つを無条件に連続呼出ししない。
- `PlanValidator`：候補外・重複・前提不足・逆順・廃止部品・目的違い・家庭許可違反を拒否。部品自体の前提グラフに循環があれば教材を公開不可。モデルが安全ラベルや前提を新設・解除することはできない。

### 入出力・状態

新job `guided_plan`。入力はv0.4と同じ親確認済み投影、本人のfocusと困り所、本人申告の完了step ID、サーバーが許可した最大12部品とその前提関係。家族全文、家計・残高、写真、能力点は送らない。予算の計算は端末／自サーバーで行い、モデルに金額を送る必要はない。

出力は `contracts/guided-plan.schema.json`。`step_ids` は実行順の最大5件、`clarify_id` は事前監修質問のIDまたはnull、`no_match` はboolean。三つの分岐を通常コードで検査する。

- 計画案：1〜5件、clarify_id=null、no_match=false。IDの並び以外にモデルが依存関係を確定しない。
- 確認質問：0件、許可されたclarify_idが1件、no_match=false。本人が目的を確認したら新しいquestion revisionへ進む。自動で再要求しない。
- 範囲外：0件、clarify_id=null、no_match=true。固定の「気になることとして残す／家族に相談」へ。別の課題で穴埋めしない。

`POST /assist/plans` は `{question_id, expected_revision, operation_id, assistance_request}`。clientは家族ID、許可部品や能力判定を送れない。返すPlanProposalは、サーバーが付けたid/revision/source_revision/catalog_version/consent_version/expires_at（15分）/originと監修表示文を含む。v0.4の認証・投影確認・予算・提供元・取消条件を再利用する。

`POST /plans/{id}/accept` は `{expected_revision, operation_id}`。本人の選択で初めて計画を採用し、体験のstepへ紐付ける。表示・採用・各step開始時に同じ権限と教材版を再検証する。実支出や共有を許可したことにはならない。B20/B30の既存記録へgoal→plan revision→step→本人の選択・結果を紐付ける。自己申告の完了は理解・自立の証明に変換しない。

「もっと小さく」はまず現在stepの監修済み小分け経路を使い、初期版では自動の再帰分解をしない。経路がない時は固定ヒントか相談へ。本人が計画の見直しを求めた時だけ追加提案を作り、既存の完了記録を消さず、新旧差分を採用操作で反映する。原文・家族返信撤回時は派生候補を失効し、他者の原文を複製して保持しない。

独自モデル、ベクトルDB、長期のモデル会話、agent framework、新しい外部サービスは追加しない。APIプロバイダーやモデルの交換は既存adapter内。新出力schemaに対応する提供元のstrict制約は実装時に公式資料で確認する。

### 作る順序と採否

1. B10〜B50は現行の固定版を作る。既存の体験Stepを利用し、万能プランエディターを前倒ししない。
2. B60を実行する場合、既存の入力投影・停止・費用制御を共通化し、next_action_matchとguided_planを個別フラグで比較する。guided_planが今回の差別化仮説、新聞AIは第二優先。
3. 固定手順／候補検索のみ／課題分解支援の三条件で、適切な最初の一歩、本人の理由、過剰分解、親の補助時間を比較する。さらに**別の類似課題をAI支援なしで扱えるか**を確認する。完了率・利用時間だけでは採用しない。
4. 合成の契約・意味検査に重大違反0が技術ゲート。人の評価はv0.4のAI41を併用し、支援なし条件での判断品質を落とさないことを追加する。少人数の観察で教育効果の確証とはしない。効果・費用・親負担が改善しなければOFFのまま。

| 未実行の受入仕様 | 期待する動作 |
|---|---|
| GP01：あと500円、比較に困る | 同じ目的の監修部品だけで前提を満たす1〜5手順。買うことを正解にしない |
| GP02：目的が未確定 | 監修質問1件だけ。勝手に節約や労働を目標にしない |
| GP03：候補外／重複／前提抜け／6手順／循環教材 | 拒否して固定版、実行しない |
| GP04：半分完了後に細分化・後着応答 | 完了記録と本人選択を保持、未採用の後着案で画面を交換しない |
| GP05：別家庭／同意・返信撤回／版変更／期限切れ | 呼出し・閲覧・採用・開始の各経路で拒否または失効 |
| GP06：手順完了・長時間無反応 | 自動採点・進級・ヒント剥奪なし。「自分でやる」とヒント再表示を両立 |

## Codexのスキルレビュー結果

新しい「AIエンジンスキル」を増やす必要はない。開発スキルは作業方法であり、製品内のAIの知能ではない。**不足はエンジンの契約と既存実行スキルの依存・手順対応だった。**

- プロジェクト2スキルは本文を同梱済み。UIスキルは子の主導権・共有の統一・動き・固定版比較を扱い、今回も適用可能。
- SuperpowersとVercelは今の環境でinstalled=trueを確認。必要な本文も存在。別Codex環境への導入完了とは言わない。
- executing-plansが利用するworktree・最終review・finishのスキルが登録から漏れていたため追加。新プラグイン導入は不要。
- 計画のB10見出しをtask-briefが認識できず実際にexit 3になった。Task 1〜7を併記し、冒頭の追補を各taskに移して取りこぼしを解消する。
- この環境はCodex CLI実行体がなく、リポジトリは文書の作業コピー。インストールから製品ビルドまで実行できたとの主張はしない。移行手順と工程別確認は `docs/workflow/CODEX_PREFLIGHT.md`。
