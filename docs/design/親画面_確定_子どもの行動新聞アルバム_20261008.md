# 【確定版】親への見せ方：子どもの行動・判断の過程・新聞・アルバム
2026-10-08｜UI/UX設計確定 v2／実装引継ぎ用。画面案の確定であり、家庭での有効性や本番実装を証明するものではない。

## 0. 決定事項：画面は2つ、情報の深さは可変

**親ホーム（ぱっと見る） → 出来事の記事詳細（詳しく見る）** の2つを主要画面とする。記事内で「どうしてこうなった？」「元の発言・写真・記録」を展開でき、別ページに飛ばない。承認のための確認シート／詳細は**記事の内容と条件を確認する操作状態**であり、3番目の「成長を読む画面」にはしない。

**事業の中核**は、AIが子の行動の途中と後で必要なことを自然に聞き取り、本人の言葉・報告・確認済み情報から記事を構成して、**同じ記録を子どもの非公開アルバム、親の閲覧記事、承認を得た祖父母向け新聞へ再利用し、後から振り返れること**。親向けの「3秒要約」はこの記録を読みやすくする**入口**であり、記事そのものの価値の代わりではない。

親ホームと記事の**構造・ボタン位置・状態ラベル・共有先・権限・金銭の扱いは固定**する。**記事タイトル、本文、写真の配置、重点箇所、表示ブロック、根拠付き比較／会話／時系列**は毎回の実記録をもとにAIが選ぶ。ただしAIによる自由HTML生成・権限変更・自動承認は不可。用意した安全なUI部品を組み合わせる。

> 原則：**聞いていないことは書かない。本人が言ったことも本人の申告として扱う。AIが教えたことと本人が自分で考えたことを区別する。記事にするために行動を止めない。**

## 1. 親ホーム：スマホを開いてすぐ分かるもの

### 1.1 表示順・密度を確定

1. **本当に判断が必要な依頼があるときだけ**：「はるちゃんから確認 1件」。種類と対象を一行で示し「内容を確認する」。複数件なら件数と最新の重要1件＋「すべて」。**完了報告だけを未承認クエストとして偽装しない**。親の確認権限がない案件を依頼に含めない。
2. **はるちゃんの新しい記録1件**：日付・小さな任意画像、記事見出し1行〜2行、出来事要約は**2行以内**、状態を短く添え、「記事を読む」。例えば本人の報告中なら「買い物と料理をしたと報告」。
3. **祖母／祖父の近況**：既存PR #17のコンパクト表示を再利用。「今日も元気だよ」の最終本人発信・本人手入力歩数。未送信は中立表示。**健康／安全確認済みとは呼ばない**。
4. **アルバムを見る**：一つの控えめな一覧リンク。数年前の記録の閲覧へも行ける。未公開・親未確認の記録を祖父母に自動公開しない。

依頼ゼロの日には大きいゼロ件カードを出さず、最新の子の記事を最上部。新しい子の記事ゼロなら「最近の記録はまだありません」と簡潔に出し、以前の記事入口を維持。祖父母不参加の家庭では近況の無駄な空白を作らない。

**表示例（全て仮データ）**
\`\`\`text
今日の家族                               更新 12:06
┌ はるちゃんから確認 1件 ───────────┐
│ 🍛 夕飯の実行報告／40Pの達成確認待ち │
│ [内容を確認する →]                  │
└───────────────────────────┘
はるちゃんの新しい記録
🍛 安い店から、帰宅時間に合う店へ
2店を比べ、家族に相談して選び直したと報告
[記事を読む →]            ［本人の報告］

家族の近況
👵 今日12:06「元気だよ」· 5,200歩（手入力）
👴 今日の連絡は未着 ／ 前回：昨日

[過去のアルバムを見る →]
\`\`\`
UX目標は「3〜5秒で新着と確認待ちを識別」。**実測ではない**。記事の過程の全テキスト・会話ログはホームに置かない。

### 1.2 親ホームからの遷移

- 新しい記録カード全体→該当**記事詳細**、戻る→ホームで元の位置へ。
- 確認カード→同じ対象の記事の該当確認内容へ**直接**。金額・条件・権限等を必ず表示し、別の確認操作が必要。記事を開くだけでは承認されない。
- アルバム→**記事の一覧・探索**（2つの主要閲覧画面のうち記事のコレクション入口。独立した承認画面ではない）。
- 祖父母カード→PR #17既存の個人近況・履歴へ。本人発信＝安全を証明したこととは表示しない。
- アプリ内通知・将来の外部通知→**特定の依頼または記事に直接**。親に毎日アプリを開く義務を作らない。

## 2. 記事詳細：読むのが楽しく、深掘りもできる

「AIの活動レポート」や「採点表」ではなく、**あとからも見返したい本人の経験の記事**にする。親が見たいのは結果だけでなく、本人が何を試し、なぜそうしたか。ただし理由を必ず要求したり、必ず判断変更を作ったりしない。

### 2.1 初期表示（上からの順は固定）

**ヘッダー**：戻る／日付／記事タイトル／記録・確認状態。記事名は子に通じる自然なことば。自動で「才能」「成長」「成功」と点数づけしない。

**冒頭 1〜3文**：①何を目指したか ②記録がある行動・判断の中心 ③何が起きたと本人が報告したか。**ここだけ読んでもその日の経験が分かる**。自分でやったこととAIから示された候補を混ぜない。

**実体験の核（記事の本文）**：写真が本人許可された場合は適切な位置に配置。本人の原文・特徴的な選択・やり取りを含む**1〜3個の内容ブロック**をAIが選び、必要な段落を編集する。
使える安全な種類：
- \`agreement\`：自分の希望／家族と約束した範囲
- \`discovery\`：調べる前の予想・見聞きしたこと・発見
- \`dialogue\`：聞く→返事→本人が次にどうしたか。直接確認した発言と伝聞を区別
- \`revision\`：最初の案→新情報→案の変更。実際に変更した記録がある時のみ
- \`comparison\`：予算・時間・量・店の選択。**比較した元データと時点がある時のみ**
- \`attempt\`：試してみたこと、失敗・中断、分かった結果
- \`photo\`：本人が残し家族に共有許可した画像＋説明。写真必須ではない

**本人の声**：意味ある本人の言葉が**実際に記録された時のみ**引用カードを1つ配置。本人原文が無い時、AIが「〜と話しました」を創作しない。AIが編集した本文と引用を視覚的に区別。

**結果と確認**：最後に、「本人の報告」「親が確認済み」「まだ途中」「行動なし／予定だけ」等、**何が実際に確認されたか**を簡潔に表示。親の確認待ちは報酬・安全・公開などの具体的な独立依頼へリンク。親の文章修正が本人発言に上書きされることはない。

**続きを読む**：折りたたみ2種「最初からの経緯」「元の記録・発言・写真」。必要な親はここで順に辿れる。**初期状態で詳細ログ・音声の全逐語録を広げない**。

### 2.2 展開時（別ページにはしない）

- 「どうしてこうなった？」は**実際に存在する節目だけ**を時系列に見せる。誰がいつ／どの情報を知り／本人が何を選び／何を試したかを出所付きで表示。
- 引用や数値にタップで原記録のテキスト・認識訂正・写真・確認者へ。常時録音を前提にしない。記録が消された／非共有なら非表示＋簡潔な説明。
- **本人の未発言の内面、親の未確認返答、値段・歩数・写真の未入力分**は補完しない。「空欄を埋めるための聞き直し」はしない。
- 記事が短いときは**無理に展開ボタンを出さない**。画像なし・1発言だけでも価値ある記事を成立させる。

### 2.3 記事に必要な独立操作

- 親の**本人報告の確認**は活動内容と家族の合意を見て「確認する」「あとで」。ポイント付与は事前合意・実行確認の後に一回だけ。記事を読んだからポイント確定ではない。
- **開始許可**、**達成確認**、**記事の祖父母公開**、**ごほうび交換**は**別の依頼**。一つの「全部承認」に集約しない。公開は子の共有意思＋親の一致した版・素材・宛先承認。子が拒否したら祖父母は見られない。
- 報酬はポイント残高と現金支出・提供完了を区別。特典の依頼は現時点で有効な残高・予約状態・条件に沿って初めて可能。
- この記事を訂正するとき、確認前の修正と確認済み版の更新を区別。親による重要変更は子本人の再確認が必要で、既に祖父母へ送った古い承認を自動再使用しない。

## 3. 記事は3シナリオに固定しない：実際の記録で重点を決める

3つは**記事生成の代表検証ケース**であり、AIが場面IDだけで記事の型を決めるのは禁止。同じ夕飯でも、店比較・父への相談・調理失敗のうち**実際の発言／行動が中心だったもの**を強調する。

### HSC-01 親子で最初の約束を決める（例0P）

**ぱっと見る**：「はるちゃんが夕飯の献立を自分で考えたいと相談。任せる範囲の確認待ち。」

**記事タイトル例**：「初めて、自分で夕飯を決めたいと言ってみた」
- 記録された**本人の希望**が冒頭。「頼まれた物だけじゃなく、献立から選びたい」などは原文がある場合だけ引用。
- 必要なら\`agreement\`を使い「本人が決める／当日相談／親と一緒」の範囲を整理。
- 本人が「予算を超えたら？」と聞いた記録があれば\`dialogue\`で親子の相談を扱う。
- 親が合意していなければ「約束確定」としない。**初回設定と夕飯実行は別**。記事は「これから始める希望」で終わってよい。

**もっと読む**：最初の希望→親へ相談→確認された合意・未確認の部分→本人が決めた次の挑戦。

### HSC-02 家の仕事・お金を調べる（例20P、家庭の事前合意のみ）

**ぱっと見る**：「はるちゃんが料理前の仕事を調べ、買い物前の連絡方法を提案。試したと本人が報告。」

**記事タイトル例**：「ご飯ができる前に、こんな仕事があった」
- 調べる前に何を思っていたか、聞いた相手、実際に分かった仕事を\`discovery\`で扱う。
- 本人の「家の材料を伝える」案に、父が「店に入った後では遅い」と答えたと本人が報告した記録があれば\`dialogue\`／\`revision\`で**店へ出る前に伝える提案へ修正**した経緯。
- 実際に材料を確認して伝えたと本人が話していれば「1回試したとの本人報告」。親確認前は実行確定・20P付与にはしない。
- 家計額は家庭のプライバシー。今回の調査記事に全所得・支出を自動転載しない。祖父母へは明示許可分のみ。

**もっと読む**：何を調べるつもりだったか→誰に聞いたと報告したか→提案と修正→実施・未実施。

### HSC-03 おばあちゃんの夕飯を準備する（例40P、家庭の事前合意のみ）

**ぱっと見る**：「2店を比較し、お父さんの迎えの条件からA店を選んだと報告。買い物と調理の実施確認待ち。」

**記事タイトル例**：「60円安いお店より、帰る時間を選んだ日」
- 4人分・予算1,000円・16:45帰宅・親と調理は**家族の実際の合意が記録されたときだけ**確定条件として扱う。
- 最初にB店920円→父への送迎相談→A店980円への変更が本人の記録にある時、\`comparison\`（価格・迎え16:30／17:00・帰宅見込み）と\`revision\`を中心に構成。
- 400g／600gの肉の判断が本人の記録にあれば、**記事の末尾の短い段落または展開内**。単価だけで決めなかった本人の理由があれば使い、なければ創作しない。
- A店で実際に購入し、帰宅し、調理したと報告した場合は**本人申告**。写真・レシートがあればそれぞれの事実にだけ紐付け。親確認前は40P未確定。
- 店比較の記録が無く、本人が調理を失敗して直した話を中心にしたなら、見出しも構成も**その出来事に切り替える**。合成シナリオの店比較を強制生成しない。

**もっと読む**：在庫・必要量→店候補→相談・交渉→選び直し→現実で試した範囲。情報が少なければ存在する節だけ表示。

## 4. AIによる聞き取り・記事化の確定契約

### 4.1 子どもからどう集めるか

**行動が先、記録は補助。** 子は外で調べ、家族と話し、実際に試す。AIとの会話、短い音声報告・選択、写真は行動を支える／残すための手段。常時録音・家族会話の無断収集をしない。アプリを閉じて行動し「聞いてきた」「やってきた」で再開できる。

**会話ごとの基本原則**：
1. すでに本人が話したことは**一度で抽出**し、形式別の入力を強要しない。
2. AIは行動を促す補助と、出来事を記事化するための確認を区別。本人が次に動けることを優先。
3. 記録が足りない時の質問は**本当に記事の意味が変わる一点**に限定して、短く非誘導的に聞く（例「A店に変えたのはどうして？」）。AIの推測を含む「お父さんに優しくしたかったんだよね？」は不可。
4. 本人が続けて話したい時は自然に聞ける。**すべての場面で質問数を固定しない**が、答えを強制したり「記事完成のための追加質問」を何度も繰り返さない。
5. 答えが無い／答えたくない→**その理由は記載しない**。必須の安全条件・親の許可が未確認なら実行の可否を保留し、文章生成で埋めない。
6. AIが提案した言葉・本人の自発的判断・家族の返答を**出所つきイベント**に分離。「AIの案が本人の考えに変わる」誤記は禁止。
7. 本人が見て「ここが違う」と直せる**記事確認ステップ**を経てアルバム保存。本人が共有を拒否しても活動とポイントの条件には影響しない。

### 4.2 事実の出所と生成ルール

記録の最小単位は \`event_id / quest_id / occurred_at / reporter / source_type / text_or_value / verification / visibility / revision_id\`。必要に応じて \`previous_choice / new_information / latest_choice / action_report\` 等へ紐付け。

\`source_type\` は少なくとも次を区別：
- \`child_original\`（子の発言・本人の意見）
- \`child_report\`（本人の実行申告）
- \`family_hearsay\`（子が報告した家族の返答）
- \`family_confirmed\`（権限のある本人が直接確認した返答）
- \`external_source\`（チラシ等、場所・時点つき）
- \`ai_suggestion\`（AIの案・説明）
- \`photo_or_receipt\`（画像の写す範囲の根拠）
- \`parent_verified\`（親がその内容を確認）

**すべての重要な記事上の主張には \`source_event_ids[]\` 必須。** 重要な数値・人物の発言・判断の変化・実行結果は、出所IDが存在し、現在の公開権限が適切な場合だけ記事化。記事の原文引用は録音・文字起こしなど確認済みの実発言の範囲のみ。AI編集文は引用符と混同させない。

- 元の選択・後の選択の両方が無ければ「考え直した」と書かない。
- 親から聞いたと子が話した内容は「はるちゃんによる報告」であり、親本人の直接発言引用にはしない。
- 本人報告だけでは「実施を親が確認した」と言わない。
- 知識・計算・店価格は根拠があり、時刻と条件が一致する場合のみ比較。整合しない場合は原記録のまま出し「確認できていません」とする。
- 声認識を訂正した場合は元記事に訂正を反映し、公開済みの記事の変更は新しい共有版の同意を必要とする。
- AIが入力から架空の出来事・感情・他人の発言を生成したら棄却。**プロンプト上の禁止だけでなく、構造化された根拠照合＋子のレビュー＋親の権限確認**の複数段階で防ぐ。

### 4.3 AIの表示選択

AIが返すのは **記事タイトル案／短いホーム要約／本文段落／使う表示ブロックIDと順番／元記録ID参照** の構造化情報。コード側が権限・写真公開・状態・文字数・数値の出所・内容バージョンを検査した後、固定のUIコンポーネントを描画。

**AIは内容の編集者であって、家族の承認者や行動の証明者ではない。** AIによる見出しはある程度の読み物らしさを出してよいが、実際に記録されていない行動を暗示する誇張見出しは禁止。

AI生成失敗・根拠不足は**保存されている発言・行動報告の機械的な日付リスト**に戻す。記事を無理に作らない選択も可能。

## 5. アルバムとして残す体験

- **一回の体験＝基本一件の出来事ID**。そこから本人アルバムの下書き／親の家庭内記事／許可済み祖父母新聞／紙の号（任意）を派生。投稿のたびに本人へ同じ情報を再入力させない。
- 過去記事の**新しい順**、月・年、テーマ（料理、調べ物、家の約束など）、写真の有無などのフィルタで探せる。ただし検索精度・必要な絞り込みは利用者テストで決める。年度初めや1年後に記事の文章を「最近の成長としてAIが自動再解釈」しない。
- 記事の中に**当時の本人の原文・選択・報告と日時**が残る。後日訂正した場合は訂正履歴を保持。年月による比較表示は「同じテーマを前はこうした／今はこうした」という**本人の記録が2件以上ある時だけ**、評価文なしでできる。
- 親は日々の新聞編集作業を強制されない。家族内保存と外部へ共有する許可は別。祖父母は許可された記事を日付別に読め、任意で「新聞号」を作りたい時だけ編む。子は祖父母への共有を拒否できる。
- 記録・写真・音声の保存期間、本人の訂正・削除、退会時の書き出し、将来本人へ渡すアルバムの権限は本番前の必須設計。**長期保存を約束するには運用継続とデータエクスポートの仕組みが必要**。単なる無期限クラウド保存を確約しない。

## 6. 状態と承認の明確な分離

| 状態／依頼 | 親ホームの表現 | 記事の扱い | 確定できる主体 |
|---|---|---|---|
| 計画だけ／これから | 「やってみたいと相談」 | 計画・希望の記録にする | 子の記録・親の条件合意 |
| 中断・一部実施 | 「ここまで試したと報告」 | 成功の物語に書き換えない | 本人報告→必要なら親確認 |
| 本人が実施報告 | 「実施したと本人が報告」 | 本人の報告の状態を示す | 子の報告 |
| 親が実行を確認 | 「親が実施を確認」 | 元の報告文・確認日を残す | 認証された親 |
| ポイント確定 | 「40P確定」（家族の合意がある時のみ） | 支払う／現金と混同しない | 家族の報酬ルール＋親の確認 |
| 祖父母への公開 | 「家族に共有済み」（宛先明示） | **子が同意した本文・写真・宛先・版**に限定 | 子の共有希望＋親の承認 |
| ごほうび交換 | 「50Pの交換依頼」 | 予約／承認／消費／提供を区別 | 残高と親の交換承認 |

複数依頼のまとめ承認・ワンタップ盲承認は禁止。承認時に安全・費用・宛先・版など本当に必要な条件は隠さない。

## 7. 受入基準（デモ・実装レビュー）

- **PARENT-01** ホームが新着・確認待ち・祖父母本人発信を3〜5秒で見分けられる作り。実測の利用者試験は別途。
- **PARENT-02** ホーム記事→詳細へ1タップ。戻るとスクロール位置保存。
- **PARENT-03** 詳細は「冒頭→体験の核→本人引用（ある時だけ）→結果→任意展開」。本人発言なしなら引用を捏造しない。
- **PARENT-04** HSC-01では希望と合意範囲、HSC-02では発見と試行、HSC-03では比較・選び直しまたは本人が本当に扱った別の中心を示す。
- **PARENT-05** 原文・数値・人物の台詞・行動結果・見出しの重要主張から元イベントへ辿れる。
- **PARENT-06** 欠測・未回答・本人が内緒にしたい記録でも記事作成を強要しない。
- **PARENT-07** 記録に無い選択変更・本人の動機・家族の発言を創作しない。誘導質問にも依存しない。
- **PARENT-08** 報告／親の達成確認／ポイント付与／祖父母公開／特典交換の状態が別。
- **PARENT-09** 本人の訂正→公開済み新版本文に無断差し替えなし。
- **PARENT-10** アルバムから少なくとも1か月前の記事を日付とテーマで探し、本人の過去の発言が読める。
- **PARENT-11** 実行はアプリ外で完結可能。記事に必要な質問で現実の行動をブロックしない。
- **PARENT-12** 同じ出来事を本人アルバム→親→祖父母へ再入力なしで扱い、共有許可は再利用しない。
- **PARENT-13** AI失敗／根拠不明時に事実記録リストへフォールバック。未確認は未確認として表示。
- **PARENT-14** 祖父母が未参加、子が共有拒否、親の確認が遅いときも記事と本人の活動記録は失われない。
- **PARENT-15** 記録へのアクセス・公開範囲が関係者の同意と製品権限に沿う（デモの模擬チェックを本番認可試験と混同しない）。

## 9. 確定仕様と未検証事項を区別

**設計決定**：2つの主要閲覧画面、必要時の詳細展開、AIが「聞く→事実から記事にする→本人が確認→記事を蓄積」する、記事の見せ方だけを可変、承認権限は固定コード、新聞／アルバムを一件の記録から派生。

**未検証**：子が自然に話せるか、音声誤認率、AIの記事選択の品質、親が短時間で理解するか／毎回保存・再閲覧したいか、祖父母新聞が交流を促すか、家庭が有料で継続するか、長期保存の費用・提供主体。実際の子ども側Codexの保存データと本仕様の照合後に実装へ進む。
