## 1. 画面の仕事・不安・成功を定義

- **利用者の用事**：孫がどんな出来事を経験し、何を選んだのか、大きな写真と短い本文で知る。伝えたい時だけ「読んだよ」「自分の経験」「質問」を返す。
- **不安**：小さい文字、専門用語、うっかり送信、返信を毎回求められる、勝手に孫を採点してしまう、AIが本人の言葉を代筆したか分からない。
- **想定環境**：スマホ片手／タブレット。祖母は記事を読むだけで完了。マイク・キーボード・会話AIを起点にしない。
- **最初の成功**：「はるがなぜA店を選んだか読めた」こと。**送信は成功条件ではない**。
- **結論**：G02は**固定の記事詳細**、G03は**固定の短い返信選択画面**。記事ごとに生成UIを変えない。

## 2. 情報階層：最初に何が見えるか

スマホ390pxでの縦の並び順（下部ナビゲーションは本文と別のレイアウト行で、記事に重ならない）。

```text
┌──────────────────────────────────────┐
│ ← 新聞に戻る               文字を大きく │  ← いつも同じ上部
├──────────────────────────────────────┤
│ 10月8日（木）  はるちゃんのおたより     │
│                                      │
│ ┌──────────────────────────────────┐ │
│ │  写真（親と子が共有を許可したもの）│ │
│ │  写真なしなら大きな題名カード      │ │
│ └──────────────────────────────────┘ │
│ おばあちゃんと食べるカレーを作ったよ   │
│                                      │
│ はるちゃんが選んだこと                │
│ 【A店で買い物をした】                  │
│                                      │
│ どうしてA店にしたの？                  │
│ 「B店は安かったけれど、お父さんの       │
│  迎えの時間を考えてA店にした」         │
│            — はるちゃんが話した言葉    │
│                                      │
│ もう一つ考えたこと                    │
│ 「大きいお肉は安いけど、今日は400gで    │
│  足りると思った」                     │
│                                      │
│ ▷ もう少し詳しく読む（任意）           │
│                                      │
│ はるちゃんにひとこと                  │
│ [♥ 読んだよを送る]                    │
│ [✉ 応援・思い出・質問を送る]           │
│ 今は返さない（読むだけで大丈夫）       │
├──────────────────────────────────────┤
│ [新聞]          [アルバム]     [今日]  │  ← 固定位置
└──────────────────────────────────────┘
```

- **重要**：写真はレビュー用の合成ダミー。リアルな製品では送信権限のある写真だけを表示。写真なしでも記事成立。新聞号の発行がなくても、共有済みの記事なら日付別で開ける。
- **見出しと内容は原文に忠実**。本例の金額・時刻は架空の代表シナリオであり実家庭の値ではない。記事に選択理由がなければ「理由はまだ記録されていません」と表示し、祖母が子を問い詰める導線にしない。
- **AIの理由は本人の理由に書き換えない**。「本人の言葉」「本人の報告を短く整理」「家族の話」「AIの提案」を区別。祖母用には主に**本人が共有を許可した理由**を1〜2件だけ目立たせ、比較の生データ・家計・ポイントは初期非表示（承認した記事本文に含まれる場合のみ表示）。
- **時系列の整理**：本人が最初にB店を希望→父に迎えを相談→A店へ変更→購入・料理した（本人の申告）。詳細開閉時は「最初の考え／確かめたこと／最後の選択」として表示可能。ただし未報告の段階を創作しない。
- **記事とアルバム**：ここは一つの出来事の読み方。アルバムへ遷移しても同じ `source_card_id` と承認済み素材・日付を再利用し、別の投稿を作成しない。

## 3. 「レビュー」を採点ではなく4つの負担別の返信にする

### A. 最小：読んだよ（G03-Q1）

G02の記事末に幅いっぱいの **「♥ 読んだよを送る」**。1回タップで `reply_type=read_ack` を一件送る。通信中「送信中…」とボタン無効。サーバーACK後「はるちゃんに『読んだよ』を送りました」。失敗なら「送れませんでした。もう一度」／二重タップを二重送信しない。本文入力不要。記事閲覧だけで自動送信しない。

### B. 一言（G03-Q2）

「応援・思い出・質問を送る」から固定の選択画面へ。3つの大きな選択カード：

| 返信種別 | 見出し | 祖母が見える短い例（**固定の下書き・選んだ時点では未送信**） | 子の画面の出所 |
|---|---|---|---|
| `encouragement` | 応援のひとこと | 「はるちゃんが自分で決めたんだね。読めてうれしいよ」 | おばあちゃんの応援 |
| `experience` | 私の経験・工夫 | 「私はお肉が余ったら、冷凍して次の日に使っていたよ」 | おばあちゃんの経験 |
| `question` | はるちゃんに質問 | 「400gで十分だと思ったのは、どうして？」 | おばあちゃんからの質問 |

**重要**：「★何点？」「正解・不正解」「よくできました（評価点数）」は使わない。経験を現在の正解として命令しない。祖母が「こうしたら？」と意見を言える余地は確保しつつ、本人の判断を上書きしない。

- 選んだ後、プリセット文を**本人が直せる入力欄**（任意音声認識でも可）へ。原文と送信先「はるちゃん」、写真や家計を共有しない旨を表示。初回はカテゴリボタン選択だけでは送らず、**「このひとことを送る」**で明示送信。
- 長いキーボード操作が苦手なら、短いプリセット文をそのまま使える。自由文は任意で、作文を強制しない。
- **代理入力**を手伝ってもらった場合は「代理入力あり」を記録・必要に応じて表示。祖母本人の意向を確認してから送る。
- 入力が空なら「今は返さない」へ戻れる。最初の記事読書位置を保存する。

### C. 返さない（G03-Q0）

「今は返さない」は常に表示。未返信を赤い注意・失敗・スコア欠落としない。読むだけで閉じてよい。新着がない時も過去の新聞／アルバム／独立した「今日」を使える。

### D. 子どもが受け取った後（C04）

子の「家族の言葉」に `おばあちゃんの経験／質問／応援` と原文を表示。**AIが祖母の文章を採点文や本人の判断理由に置換しない**。

子の任意の行動候補：
- 「今度ためしてみたい」
- 「別のことを考える」
- 「あとで読む」

例：祖母「余った肉を冷凍していたよ」→子「2日分なら、600gの方がいいかな？」と本人が選ぶ→別のクエストへ。**返信受信では循環は完了しない**。新しい行動を本人が選んで試した時に限り、`source_card → reply → seed → chosen_action → new_experience` をたどる。祖母に採用結果を無断配信しない。

## 4. 画面・状態・操作契約（G02/G03）

| 画面ID | 利用者の入口 | 主要表示 | 主な操作 | 戻り・例外 |
|---|---|---|---|---|
| G02 | 新聞ホーム／アルバムの許可済み記事 | 日付・孫の名前・写真・本人の決断理由・結果 | 記事を読む、必要なら「読んだよを送る」 | 「新聞に戻る」。読書位置維持。共有撤回で非表示 |
| G03-Q1 | G02末尾の「読んだよ」 | 送信相手と内容「読んだよ」 | 1タップ送信 | pending/error/ACK/duplicate。返信しなくても記事完了 |
| G03-Q2 | G02末尾の「ひとこと」 | 3カテゴリ、下書き、本文入力と送信先 | 返信種類を選ぶ→必要なら編集→「送る」 | 「今は返さない」、本文保持、失敗時も入力保持 |
| G03-R | サーバーから送信ACK後 | 「ひとことを送りました」＋誰へ／いつ／送った文 | 「新聞に戻る」 | 表示成功はACK後のみ、取り消し可能範囲は実APIに依存 |
| G02-E | 記事なし／権限失効 | 「このおたよりは現在読めません」 | 新聞へ戻る／別の記事を見る | 家計や古いキャッシュから失効分を復活させない |

**重要**：G03には「読んだよ」を送った上で、あとから質問を送る経路を残せるが、送信した回数で子に得点や祖母に継続圧を与えない。返信を保護者が読む権限の具体仕様は家族設定・同意モデルに合わせ、勝手に公開範囲を拡大しない。

### 応答状態（仕様案）

`idle → composing → sending → sent_ack` または `send_failed`。返信レコードの主なフィールド：
```json
{
  "reply_id": "r_demo_001",
  "source_card_id": "c_demo_curry_001",
  "source_card_version": 2,
  "recipient_user_id": "haru_demo",
  "author_user_id": "grandmother_demo",
  "author_role": "grandparent",
  "kind": "experience",
  "body": "私はお肉が余ったら、冷凍して次の日に使っていたよ",
  "origin": "grandparent_written_or_approved_template",
  "proxy_input": false,
  "delivery_status": "sent_ack",
  "idempotency_key": "sample_fixed_key"
}
```
このJSONは**モデル入出力仕様や既存DBの確定スキーマではなく、新規設計用の概念図**。実装時は現行のレコード・権限・イベントと重複させない。家族ID・記事の版・宛先はサーバー側で再検証。祖母のコメントにLLM呼び出し・子の行動更新の権限を付与しない。

## 5. デザイン基準と操作感

- **固定UI**：祖母のタブ・新聞詳細・返信カードの位置は常に同じ。生成UIは使わず、記事データだけ差し替える。写真の有無でレイアウトが崩れない。祖母のホームは新着なしでもタブ順を変えない。
- **文字／ボタン**：本文20px以上、行高1.6以上、主操作56px以上。ラベル・注記も読みやすさを個別に検証（14pxの細字を無条件に使わない）。少なくとも320/360/390/768pxと文字サイズ200%で検証。
- **視認性**：色だけで送信状態を区別しない。「送信中／送信済み／未送信」を本文で示す。緑は#176B5B、紙色#FFFDF7、暗色#172B2A（既存トークン）。コントラスト本文4.5:1・大文字3:1以上。
- **配置**：本文は上から順に読める一本のスクロール。返信フォーム／キーボードが写真・記事の末尾を覆わない。下部固定のタブは独立行。レビュー起動後は別画面で入力、モーダル重ねは標準としない。
- **動き**：記事切替は120ms以内のフェード（M05）。自動送りなし。低減設定時は即時。送信の成功演出は実際のACK後にだけ（M06）。スクリーンリーダーは「送信されました」を一度だけ通知。
- **写真**：写真の拡大はタップ任意。代替テキスト、閉じる動作、印刷は別受入。写真がない時も見出し・選択理由を大きく見せる。
- **「レビュー」と呼ぶか**：製品表示は「ひとこと返す」を第一候補。家族内のやさしい交流に合うか利用者に確認する。内部設計では `family_reply`／レビューと呼べる。

## 6. 主要な不正・欠損・失敗条件

| 試験ID | 状態・操作 | 期待 |
|---|---|---|
| GP-01 | 未公開・親確認待ちの記事を祖母が開く | 見えない。前の承認だけで表示しない |
| GP-02 | 新聞号が未発行だが記事は共有済 | 日付別新聞からG02を開ける |
| GP-03 | 写真がない | 題名と本人の言葉だけで最後まで読める |
| GP-04 | 本人が選択理由を話していない | 理由を捏造しない／理由欄を無理に出さない |
| GP-05 | 子が最初B店→後でA店 | 前後を本人の報告順に表示。AIの結論に置換しない |
| GP-06 | 「読んだよ」を一度押す | 内容と宛先を意識でき、ACK後だけ送信済み |
| GP-07 | 「読んだよ」を連打する | 同じ操作で二重送信にならない |
| GP-08 | 「私の経験」を選んだだけ | まだ送信しない |
| GP-09 | 祖母が下書きを変更 | 修正後の内容・宛先を見て送信、原文を保持 |
| GP-10 | 祖母が「今は返さない」を押す | 送らず新聞に戻る。失敗扱いなし |
| GP-11 | 返信送信時にオフライン | 入力保持＋未送信表示＋再試行 |
| GP-12 | 記事の共有を親子が撤回 | 既存G02読書画面から失効表示。新規返信不可 |
| GP-13 | 祖母の経験が子へ届く | 「祖母の経験」ラベルを保ち、本人選択へ戻す |
| GP-14 | 祖母が返事をしない | 子のクエスト、報酬、新聞の閲覧は止まらない |
| GP-15 | 別の祖母が同じ共有URLを開く | 権限がなければ内容非表示。URLを知るだけでは開けない |
| GP-16 | 祖母が200%文字／320px | 写真・記事・返信ボタン・戻るが重ならず読める |
| GP-17 | 低減モーション／読み上げ | 情報欠落なし・自動送りなし・送信確認を適切に通知 |
| GP-18 | 祖母が元気ボタンを押す | 新聞閲覧・レビューとは独立した送信。未操作を健康問題と見なさない |
| GP-19 | 返信受信後、子が候補を採用しない | 学習失敗・祖母への未採用通知なし |
| GP-20 | 写真や本文の共有版が変更された | 親子の旧承認で追加分を表示しない。公開版のみを読む |

## 7. 実家庭で先に検証すべきこと

1. 新聞の本文だけで「孫がなぜ選んだか」を祖父母が説明できるか。写真だけを見たい人には理由を押し付けない。
2. 「読んだよ」だけで十分な人と、経験・質問を返したい人がどのくらいいるか。
3. 自由文入力をしたいか、定型の選択だけでよいか。親の入力代行が必要な場合の操作負担。
4. 祖父母のレビューが子の判断を変えるかではなく、**どのような言葉が負担／喜びになるか**を先に聞く。
5. 5秒以内に「新聞を読む」「ひとこと送る」「閉じる」が分かるか。本文20px・56pxボタンでも文字拡大時に欠落しないか。

試験人数の一般化・「祖父母のレビューは必要」の市場証明はまだない。既存の家族アルバムやLINEとの違いは**子本人の選択理由と過去の判断を見られること**という価値仮説にとどまる。

## 8. Codexへの実装引き継ぎ境界

- 現在Codexが進める本体コード・作業ブランチには**自動でマージしない**。G02/G03が必要になった段階でこの設計を先にレビューし、権限境界・AIの出所・既存コンポーネントの状態契約と照合する。
- 最初に固定のG02記事詳細／G03短い返信のコンポーネント・データ契約・空状態を作り、AIが生成した自由なUIは採用しない。
- `source_card_id` と許可済みの `version` と送信先の認証・同意をAPI側で強制し、画面上の `published` ラベルだけを信用しない。
- 祖母は「孫への評価」ではなく「感想・経験・質問」を送る。モデル生成・レーティング・自動能力認定・報酬の付与は行わない。
- 実装・動作チェックが終わるまで本稿は**提案**。現状の `current/PROJECT_STATE.json`（main）における `implementation_allowed=false` と、新しいCodex作業の権限・段階は別途確認する。
