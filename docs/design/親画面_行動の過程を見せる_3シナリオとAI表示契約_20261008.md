# 親画面｜子どもの「行動の過程」を理解できる 3シナリオ設計 v1
**2026-10-08｜DESIGNレビュー／実装しない。検証前の提案**  
対象：忙しい小学5〜6年生の保護者。既存の祖父母近況ホーム（PR #17）に、子どもの実際の行動・判断変化・許可／達成／報酬依頼を追加する**設計のみ**。子ども画面を改良中のCodexには変更を加えない。価格・時刻・発言・Pは**架空の一家庭シナリオ**で実績ではない。

## 0. 結論（この一文に反するUIを作らない）

**親には、初見で「何が起きた／何の判断が必要」、開いたら「本人が最初どう考え、何を確かめ、誰の返答で、なぜ変え、何を実際に試したか」を示す。** 長い音声ログやAIとの全会話を毎回見せない。ただし、AIがまとめた重要な文は必ず本人の発言・家庭からの報告・計算・証拠へ辿れるようにする。

「クエスト完了」は一種類ではない。**本人の実行報告**／**親による達成確認**／**ポイント確定**／**祖父母への記事公開**／**特典を実際に提供**を別状態として表示する。「承認」も開始許可、達成確認、共有許可、特典交換承認が異なる。これを一つの大きな「承認」ボタンにしない。

父母の保護者画面は**ひとつに統合**する。母が公開、父が報酬という役割固定に戻さない。誰がどの承認権限を持つかは家庭の設定・認証側で扱う。

今回の推奨：「**固定の親ホーム＋根拠付きAI編集の出来事ダイジェスト＋重要箇所ごとに可変の比較・交渉・条件カード＋根拠タイムライン**」。AIに自由なHTML・権限変更・金銭操作をさせない。

### 1.1 競合が満たしていること／仮説上の空白

既存サービスは作品の記録、通知・承認、報酬の状態を別々に解いている。**複数の外部制約と家族の返答を受けて、本人がどう判断を修正し、現実に試したか**を根拠付きで短く示す領域に、やってみクエストの差別化仮説がある。ただしこれは**競合全製品の機能欠落が立証されたわけではない**。画面上の優位性と親が実際に対価を払うことも未検証。

## 2. 親のジョブと3層の情報設計

### L0＝3秒「今日は何があった／何を判断する？」

親ホームの既存祖父母カードを尊重しつつ、その上に**必要な依頼がある場合に限り**「はるちゃんからの確認：n件」を1行〜1カード置く。その下に「はるちゃんの今日／最近」の**最大1件**を置く。祖父母近況は後段に独立。依頼がなければ「確認待ちは0件」の大きな空カードを置かず、直近の出来事を先に見せる。

\`\`\`text
✦ やってみクエスト     今日の家族
[はるちゃんから確認 1件]   → （必要な時だけ・内容別の入口）
  夕飯の実行報告：40Pの確認待ち
  ※ごほうび50Pの依頼は20P+40Pが親確認済の別の時点でのみ成立

はるちゃんの今日
🍛 夕飯の買い物と料理をしたと報告
  920円の店も調べた → 家族の時間で980円の店に変更
  [どう考えたかを見る →]

👵 おばあちゃん 今日12:06 元気だよ · 5,200歩（手入力）
👴 おじいちゃん 今日はまだ連絡なし
\`\`\`

ここに書く「した」は正確には**本人からの実行報告**。親未確認の時は「完了しました」と断定しない。上の件数・名前・金額は各シナリオを説明する**合成画面例**であり、実際の同時に存在する真の注文ではない。**別途合意済みのPが不足している時の50Pの依頼はここに成立させない**。表示はサーバー状態から導出した正しいイベントのみ。

### L1＝10〜20秒「この出来事の価値は何か？」

カードから直接1つの体験詳細へ。最初の画面内の順はいつも同じ：

1. **何をしたか／今の状態**（本人の実行報告・確認待ち・親確認済み）
2. **大切だった判断／変化（1行）**。行動の変化が無い時は、本人の最終選択・相談した条件など最も意味ある行為1つ。AIが「成長した」と勝手に評価しない
3. **本人の言葉（1引用）**。引用に元記録ID・タイムスタンプがある
4. **今回の過程を知る主要カード（最大2〜3）**。シナリオにより「約束の表」「改善した順番」「店選びの比較」が違う
5. 今必要な確認があれば、**その依頼の内容にだけ関係する操作**。詳細閲覧が自動承認ではない
6. 「全体の経緯・元の発言を見る」（L2）。

感想や報酬のために全発言を読み切る必要はない。一方、**費用・外出・共有・約束変更に関わる判断では重要条件を折りたたまない**。

### L2＝30〜90秒「どこからその要約が出た？」

「経緯を見る」を押すと、**3〜5個の節目のタイムライン**を表示。各節目は「誰」「何をした／聞いた」「いつ頃」「根拠・確認状況」を表示し、任意で全文に戻れる。元データが少ない時は1〜2個で成立し、5個無理に生成しない。会話量ではなく**判断が変わった箇所・現実の行動とその根拠**を選ぶ。声の全録音は不要／デフォルト非保存。音声の文字起こしは本人訂正済みの範囲を優先。

注意：L1/L2の「3〜5」「10秒」はUX仮説上のデフォルトであり、固定の必須ステップ数ではない。

## 3. シナリオ別の表示契約（全例合成）

### HSC-01 初回の約束：親子で決めた「任せる範囲」を伝える

**親が知りたいこと**：はるの希望、何を任せると合意したか、何は引き続き親と相談か、親から見て未確定が何か。「初回設定完了」のチェックだけでは価値がない。0Pが例。

**L0ホーム**：
\`\`\`text
🍽 はるちゃんが「夕飯を決めてみたい」と相談
   はじめは献立と買い物も希望 → 家族と一食分を約束
   家庭の約束：親の確認待ち［内容を見る］
\`\`\`

**L1詳細（先頭画面）**：
\`\`\`text
初めての「自分で決める」相談     [約束・確認待ち]
本人の希望：「頼まれた買い物だけじゃなく、献立から考えたい」
┌ 今回、任せる範囲 ────────────┐
│ はるが決めたい：献立、買うもの       │
│ 当日相談：人数、予算、店・道         │
│ 一緒にやる：調理、荷物が多い時       │
└────────────────────┘
いちばん大事だったやりとり
 はる「予算を超えたら料理を変えていい？」
 親（本人が聞いたと報告）「人数と時間が合えば相談して変更」
→ 家族の約束の確認［承認設計は別仕様・この段階では操作しない］
次は「料理前の仕事を調べる」を本人が選択（予定・未実行）
［どう話して決めたか／元の言葉］
\`\`\`

**L2根拠線**（優先3〜4場面）：本人の希望 → 親へ許可範囲を聞いた（本人申告） → 新しい条件で本人が問い返した → 次に調べることを選んだ。**家庭の合意は本人の報告だけなら確認待ち**。親が本人として確定した返信と取り違えない。

**親が把握する変化**：「頼まれたことだけ→何を自分で決めたいか言い、約束の範囲を確認」まで。実際の料理実行・金融能力向上とは表示しない。

### HSC-02 家の仕事・お金の調査：見えない作業と「提案の修正」を伝える

**親が知りたいこと**：聞く前の認識がどう変わったか、家庭で誰に聞いたか、具体的にどの提案をどう直して試したか。家庭内の収入40万円・一部支出19万円などの合成家計額は、**親向けでも閲覧権限を明示**。祖母へは自動公開しない。

**L0ホーム**：
\`\`\`text
🔎 はるちゃんが買い物前の連絡方法を考えた
   父の意見を聞いて「店に入る前に伝える」方法へ修正
   1回試したと報告 ／ 調査20Pの達成確認待ち
\`\`\`

**L1詳細**：
\`\`\`text
買い物前に材料を伝える方法を考えた     [本人の実行報告]
最初に考えていたこと
 「買い物して料理すれば夕飯はできる」
新しく聞いて気づいたこと
 ・母：調理の前に在庫確認と献立決め（はるの聞き取り）
 ・父：仕事帰りは店に寄り、家の在庫を見られない（はるの聞き取り）
   ※直接の本人確認がない親の発言は「はるが聞いたと報告」
┌ 提案が変わったところ ──────────┐
│ はじめ：家にあるものを父に知らせる     │
│ 父の返答：「店に入ったあとでは遅い」    │
│ 変更後：「寄る日を先に聞いて、出発前に伝える」│
└────────────────────┘
実際にやったこと
 「米・玉ねぎ・にんじん・ルーを確認して知らせた」と本人が報告
親に必要な確認［合意した活動の実施確認は別判断］
［誰に何を聞いて変えたか／元の記録］
\`\`\`

**L2根拠線**：最初の考え → 母・父へ聞く → 重複購入の情報のズレに気づく → 最初の提案 → 父の返答（本人の伝聞）→ タイミングを修正 → 一度試したとの本人報告。AIが確認できない家計支出を補完しない。

**親が把握する変化**：金額計算より**情報の流れを調べ、家族の都合に合わせて提案を修正し、現実に試したと報告した**。聞き取りや交渉をした事実の確認レベルは表示。相手の発言をAIの捏造引用にしない。20Pは**親確認後に初めて確定**。

### HSC-03 祖母を迎える夕飯：複数の条件を比べ「選び直した理由」を伝える

**親が知りたいこと**：本人が献立・必要量・家の材料・候補店・送迎時刻・予算をどうつなぎ、どの判断をどんな理由で変えたか。金額が安かったことと良い判断だったことは同義でない。

**L0ホーム**：
\`\`\`text
🍛 はるちゃんが4人分の夕飯を準備したと報告
   安いB店920円 → 迎えの都合でA店980円へ変更
   親と調理したとの報告 ／ 40Pの達成確認待ち
\`\`\`

**L1詳細**：
\`\`\`text
家族で食べるカレーの材料を選んだ    [本人の実行報告・親確認待ち]
本人の言葉「安いB店も考えたけど、帰る時間に合うA店にした」
最初の条件（家庭の約束）：4人／予算1,000円／16:45帰宅／親と調理

┌ なぜ店を変えたのか？ ───────────┐
│                   A店         B店 │
│ 買う物・同じ量    980円        920円 │
│ 父が迎えられる時刻 16:30        17:00 │
│ 16:45までの帰宅約束 ○候補        合わない │
│ → はるの選択：A店                    │
└────────────────────────┘
売り場で、もう一つ考えたこと
 肉400g 520円／肉600g 600円（単価は大きい方が安い）
 でも600gなら買い足し総額1,060円・予定の1,000円を超える
 → はる「今日は400gで足りる。トマトも買いたい」
実際にやったこと（本人の報告）
 A店で980円購入→16:40帰宅→家族と調理→17:30食事
 ［写真・領収書・親の直接確認があれば別出所で添える。無ければ申告］
親の達成確認40Pは別操作。祖母への共有も本人の希望＋保護者の別承認
［どこで判断を変えたか／原文を見る］
\`\`\`

**L2根拠線**（代表5節）：今日の家の在庫を現物確認 → 同じ量で2店のチラシを調べた → 父へ送迎を頼み返答を聞いた → A店へ選び直した／父の再合意 → 売り場の400gと600gを比較 → 現実の買い物・調理を申告。シナリオ上は6節になる場合もあり、**意味のある節は潰さない**。店頭価格・持ち帰り・現実の支出は別イベント。AIが実施確認を創作しない。

**親が把握する変化**：「最安の店」から「予算・必要量・時間・家族の協力を満たす店」へ、本人が理由を話し選び直したこと。ここまでが**この場面で示せる判断の記録**。能力向上・将来の投資判断力の向上は証明できない。

## 4. 依頼と近況の一体化：混ぜないが離し過ぎない

### 4.1 親ホームの並び順（新規件数に応じて固定ルールで決める）

1. **今必要な判断**（あれば）：保護者が実際に権限を持ち、期限や費用に関わる依頼カード。上位表示。複数なら「n件」を押し個別カードへ。AIは並び替えや自動承認しない。
2. **はるちゃんの直近の活動**：最大1件。完了申告・途中・約束確定のどれかを正確に記述し、重要な判断の一文を添える。「すべて見る」からアルバムへ。
3. **祖父母の近況**：PR #17既存の親カード（元気発信・歩数は本人入力）。健康診断を装わない。

子の実行報告を「クエスト達成！」と大きく見せて、親へ確認を押し付けるのは不可。未確認は未確認とする。

### 4.2 許可・確認・お金の状態を分ける

| 種別 | 親に見せる例 | 実際の決定主体・条件 | 禁止される混同 |
|---|---|---|---|
| A. 初回／都度の許可 | 「一食の献立と買い物を任せたい」 | 親・子双方が用途、道、額、危険性等を合意 | AIの推薦＝許可済みとしない |
| B. 活動の実行確認 | 「買い物と調理をしたとの報告／40P確認待ち」 | 親が実際の約束・報告と範囲を確認 | 本人申告＝親確認済みとしない |
| C. 共有公開の確認 | 「祖母へ送るこの記事／写真／版／宛先」 | 子の共有意思＋親が同じ版・写真・宛先を承認 | 家庭内の記録を見るだけで祖母へ自動公開しない |
| D. 特典リクエスト | 「カフェ50Pをお願いしたい」 | 50Pを適切に予約後、親が条件を確認して交換確定→実際の提供は別 | 依頼＝消費、承認＝提供済みとしない |

子の報酬ポイントは「残高」や「家庭からの円」と別台帳。**L0の依頼カードには、誰が何をしたいか・どれだけ費用/Pが関わるかを示す**が、誤タップで金銭的な承認が成立しないよう詳細確認を経てから状態変更する。

## 5. AIが毎回「どう見せるか」を選ぶ契約：固定骨格 × 可変モジュール

### 5.1 まず、AIへ何を入力するか

家庭内の全音声や家計を生で渡さない。保存と処理の同意を分け、必要最低限の**イベントとして確定・承認された情報**だけを取得する。音声の文字起こし、家族の伝聞、AIの補助、計算結果、写真・領収書、実行申告、親確認を別の \`source_type\` で保有する。

**不変イベントの提案スキーマ（製品API契約ではない）：**
\`\`\`text
event_id                  stable ID／二重取り込み防止
quest_id, scenario_id     体験ID（HSC-01等は例の分類）
occurred_at, recorded_at  出来事の日時／入力した日時は別
actor, reporter           本当にした人／報告した人（他人の発言は伝聞）
kind                      goal | question | observation | family_report |
                          constraint | option | ai_help | child_choice |
                          revision | action_report | parent_verified | reflection
child_original_quote      子の実際の発言（認識訂正済み）／任意
source_type               child_report | parent_statement | child_hearsay |
                          observed_photo | store_flyer | receipt |
                          fixed_help | ai_generated | parent_verified
source_ids[]              原発言・価格の参照元。要約文はすべて対応づける
conditions_at_time        その時点で確認された、今回必要な条件だけ
verification             reported | corroborated | parent_confirmed | unverified
consent_scope             child_parent_private | recipient_explicit
visibility_version        本人の共有意思と親承認対象の版
status                    planned | reported | confirmed | cancelled
\`\`\`

本人原文（\`child_original_quote\`）のある箇所は引用。**親から聞いた台詞を子が伝えた場合は「はるちゃんによる親の発言の報告」と表示**。写真やレシートは実行全体の証明ではない。レシートがあっても本人による調理を自動確定しない。声データや家計の詳細が必要かは別途同意と保持期間を確認する。

### 5.2 AIの役割と自由度

1. 通常コードで日付・権限・状態・ポイント・計算・送信を確定し、子のタイムラインから権限のある情報を抽出する。
2. AIには \`events[]\` から **「見出し候補」「重要な転換点の候補」「3つ以内の過程カードID」「各文のsource_ids」** をJSON等で返させる。AIに新しい家族の行動・家計額・セリフを作らせない。
3. AIが選べる**表示モジュールは限定**：
   - \`agreement_matrix\`：本人希望と家庭の合意範囲（HSC-01に適切）
   - \`before_after\`：初案／相手の返答／修正案（HSC-02に適切）
   - \`tradeoff_comparison\`：店・時間・金額・条件（HSC-03に適切）
   - \`action_evidence\`：本人の実行申告・親確認・写真（3体験共通）
   - \`timeline\`：節目と元記録の詳細（共通）
4. 固定UIが構造化内容を表示する。AIがHTML、色、ボタン、承認の権限を直接出力・操作しない。根拠のない見出し・転換点・比較値は通常コードの検証で棄却・修正依頼。生成失敗なら機械的な時系列の記録カードへフォールバック。
5. **本人が修正した記録／親確認の変更は、要約へ再反映**。元の要約は監査版として残しても非公開要約の再生成は可能。公開版は本人共有意思と親が承認した同じ版でなければ送らない。
6. 記録の欠けやAIの不確かさを短く表示（例「本人の報告。家族の返答は未確認」）。数値のAI自己申告confidence（例「正確度97%」）だけで事実認定しない。
7. 子どもの未来の能力、責任感、性格、金融力を一枚の画面で点数化しない。推測は推測と分け、家庭の費用や意思決定に使わない。

### 5.3 どの転換点を親へ選ぶか（明示ルール＋AI選択）

最重要は**本人の希望と新しい条件の衝突**。候補の優先順位：
(1) 前の案に対して実際の人／現物／情報源から新事実が入った→(2) 本人がそれを基に選択を変えた／現実に交渉した→(3) 実施した範囲を報告し、必要なら親が確認した。単なるヒント表示、短い相づち、同じ意思の繰返しは標準で省略。

**例：なぜAIのヒント数を主役にしないか**。子が何回AIへ聞いたかより「本人が父の迎え時間を聞いて、安いB店からA店へ変更した」が重要。AIが回答しただけで子の行動を証明したことにはならない。

AI出力検査：
- \`key_claims[].source_ids\` 必須。参照元が削除・失効・未確認なら該当文を非表示／未確認ラベル。
- \`decision_change\` は少なくとも\`prior_child_choice\` と \`later_child_choice\` の二つの記録がある時のみ「選び直した」と言える。前の候補がAIだけなら「AIが候補を示した後、本人がAを選んだ」とする。
- \`action_outcome\` は \`reported\`／\`parent_confirmed\` を区別。計画・撮影・移動候補だけで\`done\`にしない。
- 親の承認ボタンは固定コードが依頼ID・版・条件を検査して設置。AIは表示のおすすめ以上をしない。

## 6. シナリオが欠けている時の画面（重要な反例）

| 状態 | L0 | L1/L2 |
|---|---|---|
| 子が「やりたい」だけ話して止めた | 「夕飯を考えてみたいと話した・まだ始めていない」 | 希望原文だけ。家族合意・実行・報酬を自動追加しない |
| 親からの返答が子の伝聞のみ | 「父へ相談したと本人が報告」 | \`family_hearsay\`。父が認証して答えたようには表示しない |
| 何かを買ったが写真なし | 「買い物をしたと報告」 | 写真なしで記録を残す。親の確認を追加で求めるかは約束次第 |
| 調査はしたが提案未実行 | 「仕組みを調べ、提案を考えた」 | 提案・実行を区別。活動全体20Pの達成を自動付与しない |
| 親に見せたくない家計項目 | 公開対象に含めない | 親の役割上アクセスがあり得ても、記録・処理同意とデータ最小化を維持 |
| AI要約に根拠なし | 「はるちゃんが記録を残した」 | 通常コードで原文・日時の一覧へ戻す。勝手に美談化しない |
| 子が祖母への共有を拒否 | 親の記録には残る（事前説明した権限内） | 祖母には見えない。ポイント・活動は続行 |
| 未承認の40P／50P依頼 | 別々の状態ラベル | 「確認前／予約中／消費／提供」を混同しない |
| 家族が忙しくて話せない | 「相談はあとで」 | 体験は途中のまま保存でき、親へ督促しない |
| 重要な失敗・予算超過 | 「計画を修正した」「途中まで」 | 成功ストーリーに書き換えず、何を変えたかを本人の言葉で残す |
| 通信・記録が未送信 | 「表示できる記録なし」 | 同期中／オフライン／未登録を区別し、架空の完了を出さない |

## 7. 親画面ワイヤー：同じ骨格に3種類の可変内容

### 親の詳細の固定レイヤー

\`\`\`text
← 今日の家族           10月8日
［実行申告／親確認済／途中／約束確認待ち］
大きい見出し：本人が今回取り組んだこと
今回の1行：何が起きた／どんな選択をした
[ はるちゃんの発言（原文）]
┌── 今回の判断を表す適切な図 ──┐
│  ① 任せる範囲の表              │
│  ② 提案：最初→相手の返答→修正    │
│  ③ A／B店：価格・迎え・帰宅条件   │
└───────────────────────┘
[実行と確認：本人報告／親確認]
[必要な判断へ進む／後で]  ← 権限型ごとの別画面
[ 何があってこうなった？ ↓ ]
  時系列：節目→原発言／記録／出所
\`\`\`

**注意：** 表に入る項目はその体験で根拠のあるものだけ。比較表の「父の迎え時間」ははるから聞いた報告ならそうラベルする。詳細が多いときは元記録へ。タイトル、タグ、親の操作、祖父母公開をAIが決めない。

## 8. どうすれば事業価値が生まれるか

**最も強い失敗シナリオ**は「AIが立派な話を作っても親は読む時間がなく、承認は面倒で、毎日開く理由もない」。また、不完全な記録にAIが意味を加えてしまうと親の誤認と子どもの不信を招く。これは見た目を改善しても解消しない。

親には（a）どこまで任せてよいか判断材料が揃う（b）子と会話を始める共通の話題が手軽に見つかる（c）自分で親が家庭教育の教材を作らなくてよい、の3価値を検証する。**「完了した数が増えた」だけでは教育効果も継続理由も証明しない**。

### 調査設計案（実施未承認・仮説検証用）

A. **方式比較**（まず紙／クリックモックで可能）：同一の合成記録を①完了スタンプのみ ②AI文章による要約のみ ③判断の転換点＋証拠の3方式で比較。順番を入れ替える。親に「子が何を考え直したか／何を実行したか／何が未確認か」を読み取ってもらう。

B. **理解**：初見3〜5秒で申告と確認待ちを混同せず、対象の一件へ進めるか。詳細は30秒程度で**少なくとも1つの事実上の転換点と、その出所**を正しく説明できるか。数字はプロダクト仮説のテスト目標であり実測ではない。

C. **実際の行動**：既存のインタビュー設計に従い、家庭の負担を測る。週のどの瞬間なら開くか、見たい記録と不要な記録、AI要約への信頼、原文の閲覧、子との会話に繋がるか、再利用の理由を観察する。PoCで実証するまでは有料継続を断定しない。

D. **プライバシー／誤認**：子の原文がない所をAIが作文していないか、親の言葉が本人の伝聞と明示されているか、家計・身体状況・家庭内葛藤が不要に共有されないか、子が「親にどう見えるか」を分かっているかを確認する。

### 仮の合格基準（実証前）

- P-AC01 親のトップ画面で「本人が何をした／いま親が何をする」を誤認しない。
- P-AC02 HSC-01では「希望・任せること・当日相談・一緒に」を説明でき、0Pを示す。
- P-AC03 HSC-02では「提案が父の返答でどう修正されたか」を読める。家計を勝手に晒さない。
- P-AC04 HSC-03ではB店920円→A店980円への転換、送迎時刻、400g／600gの条件を区別できる。
- P-AC05 各AI要約の中心の主張から1タップ以内に根拠の発言／確認情報へ行ける。
- P-AC06 断り・一部実施・欠測・非共有でも捏造せず自然な画面が成立する。
- P-AC07 親が承認していない活動を親確認済と表示しない。報酬も発行・取り置き・消費・提供を分離。
- P-AC08 祖父母公開前に子の意思と親の版・素材・宛先承認が揃っている。
- P-AC09 家族構成が異なる、親が祖父母と連絡しないなどでも出来事の価値を損なわない。
- P-AC10 親による誤り訂正と子本人の訂正が反映され、すでに公開済みの記事を無断更新しない。
- P-AC11 AI不調時、同じ権限範囲で固定の時系列と本人原文にフォールバックし、確認機能は続行できる。
- P-AC12 通知を受け取った親は対象の依頼の詳細へ直接進めるが、承認に必要な安全・金銭・宛先条件の確認は省けない。

## 9. いま決めるべきことと、まだ決めないこと

**現時点の推奨決定**：
1. 親の一覧は固定カードを採用。可変なのは出来事の見出しと1行の判断の変化。
2. 詳細は「本人の言葉＋転換点」を先頭、その後に必要な図、元の記録。情報の整合性はAIでなく構造化状態と根拠IDで保証。
3. 3シナリオに同じスロットを強制しない。HSC01は約束、HSC02は提案の修正、HSC03は条件の比較。場面ごとの重要な行為が先。
4. 完了と承認と公開とポイントを独立させる。AIがこの4種類の権限を扱わない。

**確認してから決めること**：子どもに親に見られる範囲をどう説明し選択させるか、AIの要約を誰がいつ確定するか、家族・子どもの音声／写真／原文の保存と消去、親の確認頻度と通知、AI推論の品質・費用、50Pの交換承認画面のUX、家庭内で本当に親の関心を引けるか。

**次の作業は実装ではなく検証できる3本の画面ストーリーボードと元イベントのfixture**。現行の子ども画面が記録していないデータを、親画面側であるかのように捏造する実装は避ける。Codexが作る子側の記録契約に合わせてから表示実装へ移る。
