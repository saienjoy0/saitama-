# やってみクエスト｜相談しながら製品を設計する
更新：2026-10-05。状態：設計の進め方と既存資料の見直し案。新しい製品仕様を確定した文書ではない。

## 今回の依頼と理解
創業者本人の要望を聞き、相談しながらプロダクトを設計する。そのためのスキルを先に探して取り込み、GitHubの既存設計を修正するか、一から作るかを判断する。

現在の理解は「家庭の体験で子どもが自分で判断できる範囲を広げ、その過程を家族で共有する」。中心価値の優先順位は次の対話で確かめる。創業者の希望、保護者・子どもへの調査、公開研究、設計上の仮説を別の情報として扱う。

## 既存案をどう扱うか
推奨：既存設計を基礎に、目的・初回体験・継続と購入理由を部分的に再設計する。作り直しの必要性は、対話で主要な目的や利用者が変わった場合に再判定する。

| 対象 | GitHubで確認した状態 | 今回の扱い |
|---|---|---|
| 製品の中心 | product-design-v0.1は「成長アルバム型アプリ」。ai-engine-review-v0.4.1は「判断できる小さな手順と必要な支援」が中核候補 | 本人が最も実現したい変化から、全体の定義を再確認する |
| 三者の体験 | 子の探索・選択、親の確認、祖父母の任意の返信を役割別に設計済み | 骨格を再利用。祖父母・新聞の優先度は会話で確認する |
| 初期対象・教材 | 基礎設計は小4〜6、3テーマ、4週間の提案。最近の体験設計は小5〜6を対象とする | 現行の対象と「最初の一回」を明示し直す。対象年齢を勝手に広げない |
| 記録と共有 | 共有意思、保護者確認、未返信、写真なし、撤回等の扱いがある | 再利用。記録・図・返信を毎回必須にはしない |
| 継続と購入 | 基礎設計に有料仮説がある。2026-10-05の別資料には目的→体験→次の体験→親の購入判断がある | 料金を先に固定せず、継続する理由と購入する理由を分けて相談する |
| AI | 固定教材との比較、求めた時だけのヒント、親向け下書き、失敗時の代替を設計済み | 境界を再利用。本人の判断を育てる役割と、準備の手間を減らす役割を分けて確認する |
| API・データ・権限 | 家族分離、版、同意、共有撤回の基礎がある | 維持する。相談の準備で製品コードやDBを作らない |
| 実装計画 | v0.4.1向け計画が準備済み | 合意後の設計差分を反映してから実装の対象にする |

## 対話の進め方
1. 最初は「どんな変化を実現したいか」を本人の言葉で聞く。決めた答えが資料にある場合は、候補として示して確認する。
2. 毎回、一つの重要な問いを扱う。機能の有無より、状況・困りごと・得たい変化を先に尋ねる。必要なら具体例を添える。
3. 回答に対して「私の理解」「まだ仮説の点」「次に決めること」を短く返す。回答前に全体仕様を決めない。
4. 次に、最初の子どもの体験と、親が価値を感じる場面を決める。
5. 継続、購入、三世代の交流、AI、画面を順に相談する。質問の順番は実際の回答に合わせて変える。
6. 合意した内容を既存設計の該当箇所に反映する。新しい正本を毎回増やすのではなく、判断の理由と変更箇所を既存DECISIONS／設計／FEATURE_REVIEWに結ぶ。
7. 指標の基準値が未取得なら「未計測」、予想なら「仮説」とする。テンプレートの数値・架空例を実績へ転記しない。具体的な目標値を置く場合は設計上の提案として説明する。
