# 親画面操作デモ｜今日 → 3つの記事 → アルバム → 家族（2026-10-08）

## 操作

[画面を開く](index.html)。ブラウザーでHTMLを開くだけで動く**単一ファイルの合成デモ**。家庭の実記録ではない。AI/サーバー/ネット通信/認証/ポイント確定/祖父母配信はしていない。架空の「はるちゃん」の言葉・数値・時刻・歩数はサンプル。

- **今日**：確認待ち（存在時だけ）→はるちゃんの最新記事1つ→祖父母からの近況をコンパクト表示。祖父母の「元気だよ」は本人による発信で、客観的な健康・安全の保証ではない。歩数は本人入力と区別。
- **記事詳細**：一覧/今日のカードを1タップすると、記事をその場で読む。写真風イラスト（合成SVG）、冒頭、本人の言葉、各体験に適した表示部品（約束・発見・選び直し・条件比較）、行動の状態。必要なときだけ「最初からの経緯」「元の記録・発言」の詳細を展開。
- **アルバム**：3シナリオの記録を一覧表示。テーマ別の絞り込み、各記事の開閉、前後の記事への移動。実装対象の3シナリオはHSC-01「最初の約束」、HSC-02「家の仕事とお金の調査」、HSC-03「おばあちゃんを迎える夕飯」。
- **家族**：祖母・祖父の近況、前回報告、本人入力の歩数を表示。未着や歩数を異常とは評価しない。
- **承認デモ**：はるちゃんの夕飯40Pの本人申告（親の確認待ち）→親が条件を読みチェックした場合のみ40P確定 *というデモ内状態*。その後、画面下「デモの状態を切り替える」から**50Pのごほうび交換依頼**または**祖母に記事を共有したい依頼**を発生させ、それぞれ別の確認シートで扱う。実際の送金・公開・購買・家族への通知なし。

## 事実とAIの責務

- 各架空の記事を **event_id→出所型→本人原文→確認状態** のfixtureとして記録し、表示モジュールが参照するイベントが存在するか構文実行時に検証。
- 実際のデモは「AIが編集した記事に相当する**固定の架空記事**」を3件収録している。**このHTMLはライブAIを使用していない。** 事業仕様上のAIはイベントから題名/要約/本文/表示部品の選択を提案するだけ。根拠のない出来事・感情・会話・写真、本人がしていない行動を創作してはならない。
- 「子どもが報告した」「親が確認した」「ポイントの確定」「祖母への公開」「ごほうびの交換」は別の状態。申告だけで40P付与しない。
- 3件の記事を再利用してホーム→親の記事→アルバム（祖父母新聞は外部認証と共有承認が必要でデモ内では実送信しない）。同じ出来事を何度も入力させない。
- 複数の重要な記述に原イベントIDへのリンク（モーダルの「出所を確認する」）を付け、原記録の種別や家族から聞いた伝聞を視覚的に確認できる。

## UI方針

親ホームに長いログを並べず、確認依頼と子の記事（短い要約）を最優先。「今日／アルバム／家族」の3タブ。シナリオ名に関係なく、記事の中身は本人が話した出来事に合わせて変えられる拡張可能なモジュール設計。画面や認証、権限、ボタン位置をAIに生成させない。原文が乏しい場合は短い記事で成立する。
