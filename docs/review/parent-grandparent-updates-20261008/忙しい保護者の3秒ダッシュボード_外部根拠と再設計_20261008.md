# 忙しい保護者の親画面｜Google Material × Amazon Cloudscape UX監査と再設計（2026-10-08）

**範囲**：ユーザー指示に沿い、親が祖父母からの「元気だよ」、歩数、前回連絡を素早く把握するUIを再設計する。子どものクエスト承認／ご褒美承認／行動の見せ方は**次回以降の別設計**として位置だけ示す。**この文書だけでは既存HTMLの実装を変更しない。**

## 1. UX監査：実際のスマホ確認版 390×844 から確認した問題

- 現在のスクリーンショットは「これまでの近況」画面で、ブランド帯→肩書→ページ見出し→祖母祖父の大きな選択ボタン→長い説明→各日付の大きなカード。**一画面あたりの判断情報が少ない**。
- 一目の目的が「いま何か起きているか」なのに、最初に**過去ログの閲覧**を選ばせる。日付ごとのカードは繰り返し空欄を見せる。
- 各イベントに「送信12:06／受信12:06」などの詳細メタ情報を常時表示。価値に比して視覚的負担が大きい。
- 緑の大きな選択ボタンは「何をするボタンか」より「選択中の人」を強調。健康・安否の監視画面に見えてしまう懸念。
- 「歩数の手入力と健康診断は違う」という正確な注意は必要だが、ホームに大きな説明パネルを置くのは優先度が低い。**ホームでは『本人入力』と短いラベルにし、意味は詳細と初回ガイダンス**に表示。

### 反証・分けるべきこと
- 「共働きの親は毎日自発的に開く」は事業仮説。親画面の情報設計だけでは習慣化を証明しない。
- 「今日の連絡あり」は**発信ボタンが押された自己申告**であり、安全・健康が客観的に確認できたことではない。未着・低歩数から異常・疾患・事故を推定しない。
- 祖父母の近況が1日の親の最大の用事かはまだ未検証。子の確認待ちと並列で比較する必要がある。

## 2. 公式UX一次資料：何を転用し、何を転用しないか

| 出典 | 公式の原則 | この画面への適用 |
|---|---|---|
| **Amazon AWS Cloudscape / Static dashboard** https://cloudscape.design/patterns/general/service-dashboard/static-dashboard/ | 数秒で要点を把握、上部は最も重要な状況、詳細ログを避ける。モバイルは意味のある行動可能情報へ | 最初の画面を今日の概要にする。履歴は2次画面 |
| **Amazon AWS Cloudscape / Dashboard items** https://cloudscape.design/patterns/general/service-dashboard/dashboard-items/ | 1項目は1目的。主要アクションは1つ。長い表・ログと複雑な操作は詳細へ | 祖母と祖父はそれぞれ「連絡＋歩数＋前回日付」の1行〜1カード。個別ログを展開時のみ |
| **Amazon AWS Cloudscape / Static vs configurable** https://cloudscape.design/patterns/general/service-dashboard/ | 重要な項目の順が利用者にとって決定的な時は固定ダッシュボード | 親ホームは配置を固定、カード内容だけ更新。AI生成UI・ドラッグ編集なし |
| **Google / Material UX Writing (2026)** https://codelabs.developers.google.com/codelabs/material-communication-guidance | 簡潔で正確な文章。限られた内容、直接的な言葉を使う | 「今日の連絡 12:06」「5,200歩・手入力」「今日はまだ連絡なし」に短縮 |
| **Google / Android navigation** https://developer.android.com/design/ui/mobile/guides/layout-and-content/layout-and-nav-patterns | 主階層のナビは3〜5項目が一般的。頻出操作は少ない深さへ | 現時点の「今日と履歴だけ」ならホームと詳細リンクで足りる可能性。将来の3タブ「今日／確認／記録」は子承認仕様決定後に検証 |
| **Google / Android notifications** https://developer.android.com/design/ui/mobile/guides/home-screen/notifications | 要約・文脈・行動を伝える。過度な通知を避け、選択可能にし、私的情報を保護 | 「祖母からおたより」等は控えめに。子の承認が必要なら対象へ直接遷移。未送信を自動で危険通知しない |
| **Nielsen Norman Group / Progressive disclosure** https://www.nngroup.com/articles/progressive-disclosure/ | 高頻度・重要な情報を先に、まれな詳細は必要時に表示 | 受信・送信の二つの時刻、過去7日、取得元の説明は詳細画面 |
| **Google / Accessibility** https://developer.android.com/guide/topics/ui/accessibility/apps.html | 少なくとも48dpのタップ可能領域を推奨 | 主要行の全幅タップ、下部固定ナビはコンテンツを隠さない |

※ **CloudscapeはAWS管理画面向けのデザインシステム**であり、Amazonの小売アプリや家庭用アプリそのものではない。**概念を転用する**のであって、管理コンソール風の見た目・情報密度を再現しない。

## 3. 親の主な利用意図：3秒／10秒／30秒の仮説

- **3秒：何が来た？** 今回の祖父母の最新連絡、本人の最後の送信日、誰に対応が必要か（将来の子の承認）を見分ける。
- **10秒：必要な操作をする** 届いたカードを開く。将来、はるちゃんの承認があれば要件を見て適切に承認／保留する（内容確認なしの盲承認はしない）。
- **30秒：詳しく知る** 祖母1人の7日履歴、送信／受信時刻、歩数手入力の詳細、必要なら本人へ連絡。

この秒数は研究の実測値ではなく**このアプリで試すUX目標**。

## 4. 推奨「今日」のホーム（親の行動がない現時点）

```text
┌─────────────────────────────┐
│ ✦ やってみクエスト     [家族] │
│ 今日の家族        最終更新12:06│
│                             │
│ 👵 おばあちゃん          ›    │
│ ♥ 今日も元気だよ    12:06     │
│ 👣 5,200歩 · 本人入力         │
│ ─────────────────────────── │
│ 👴 おじいちゃん          ›    │
│ 今日の連絡はまだありません     │
│ 前回：昨日 19:10             │
│                             │
│ [ 過去の近況を見る › ]        │
│                             │
│ （この先、必要に応じて）        │
│ はるちゃんの記録／確認：別設計  │
└─────────────────────────────┘
```

- 祖父母は1人を一枚の**コンパクトな2〜3行リスト**。現行の2×2情報ブロックやログカードの入れ子を廃止。
- 情報の高さをまず縮める。上部の警告や長い説明パネルをなくし、信頼上の重要注意は短い「本人入力」「最終受信」ラベルと詳細内の一文で伝える。
- **見た目の明るい緑のチェックを『健康OK』の代わりに使わない**。連絡受信は中立の情報。未着も赤にしない。
- 歩数が届いていない場合は「歩数：記録なし」で、昨日の数字を今日の数字として見せない。日付が跨げば自動で「今日はまだ連絡なし」。
- 見出しのラベルはそのまま「今日の家族」。仮にお知らせがある場合は補足として表示。ホームで全履歴を生成しない。
- **祖父母への連絡手段**：実際の電話・メッセージ連携の可否は別設計。デモでは押せないボタンを置かない。

## 5. 将来の子ども承認を入れる時の場所だけ確保

```text
（必要な確認がある場合だけ）
「はるちゃんから確認が1件」→詳細の「何をする・費用・相手」を読む
それ以外は祖父母の今日の近況が最初
```

日々の可視化と意思決定が異なるため、**承認を祖父母の近況に混在させない**。依頼詳細・契約／金銭の安全条件は次回設計。確認が0件で空の巨大カードを出さない。**子が何をしたかの成長見せ方も今回決めない**。

## 6. 通知／起動をどう考えるか

「親は時間がある時に自発的にすぐ開く」は未検証。通知から入るケースと、親が気になって開くケース両方に最適化する。

- 承認が必要な行為：将来、親が決めた通知設定と子どもの約束に沿い、必要な時だけ通知。通知から詳細へ直接開く。ただし本文・相手確認なしで処理完了にしない。
- 祖父母の元気連絡：静かな通知・日次まとめ・通知なしを選べる提案。本人の個人情報はロック画面で隠せるようにする。
- **未送信をもって緊急通知を出さない**。そのような機能は安否確認サービスとして別の要件・救済手段・同意が必要。
- 必要な時に子と祖父母の両方の用件を一覧で把握できるようにしつつ、通知件数だけで不安を煽らない。

## 7. 受入テストと判断条件

1. 保護者8〜12名程度への試作ユーザビリティテスト（探索目的、母集団の実証ではない）。**最初の5秒で**「祖母から今日は来たか」「祖父はどうか」「歩数の出所」を説明できるか。スクロールなしの読取率を記録。
2. それぞれの行について「今日未着」と「危険・体調不良」を誤同一視しないか確認。
3. 履歴への到達タップ数と所要時間：目標は1タップで祖母の履歴を開く。履歴への往復で元の位置を保持。
4. 行動のない日：親が開いて何も変わっていない時に「無駄な時間だった」「また開きたい」と感じるかを聴く。これは製品の継続利用に直結する。
5. 短い通知と日次まとめの比較：通知開封率だけでなく、通知オフ・ミュート・再訪を観察。
6. Android幅320/390、文字200%、スクリーンリーダー、通信遅延／失敗、日付境界（タイムゾーン）を試験。
7. **未着とエラーを区別**：今日本人から未送信・通信失敗・同期中・家族設定未完は別メッセージ。すべてを「今日の連絡なし」にまとめない。

## 8. 次に作るもの（ユーザー確認後）

**今の親画面のコードはすぐ装飾でパッチしない。** まず上記ホームの低忠実度UIを固定、テスト用に「今日来た／来ない／データ取得失敗」の3ケースを実装し、優先順位と画面高さをレビューする。その後、既存PRの祖父母送信コードとの接続と履歴を維持する。子どもの承認UIは後日別スコープ。
