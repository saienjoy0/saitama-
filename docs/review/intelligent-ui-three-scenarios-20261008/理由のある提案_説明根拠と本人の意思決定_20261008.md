# やってみクエスト｜理由のある提案 → 本人の検証 → 判断 → 理由の記録
更新: 2026-10-08 / 種別: 発表用UI・合成シナリオ設計案 / 本体: DESIGN・D90（実装未承認）

## 今回の設計判断

AIがただ「次に冷蔵庫を見て」と言うのではなく、**なぜその候補が本人に合いそうなのかを、確認できる情報に結びつけて短く説明する**。ただし「すべての説明を毎回長く読む」のではない。画面上は①ひとこと提案理由、②「何を根拠にしたの？」で開く確認情報、③本人が選ぶ／別案を選ぶ／確かめに行くという構造。

これは**モデル内部の隠れた推論過程を表示する要件ではない**。利用者に示すのは、根拠の出所・条件付きの見込み・未確認項目・比較する条件に限定する。モデルに後付けで架空の説明を作らせない。

## 厳密に区別する情報の種類

| 種類 | UIのラベル | 例 | 扱い |
|---|---|---|---|
| 過去に記録された内容 | 前回の記録 | 米・玉ねぎ・にんじん・ルーがあった | 時点と出所を示す。今日あるとは扱わない |
| はるちゃんが今回話した内容 | はるちゃんの報告 | 家庭科でカレーを作った経験がある | 本人の言葉として保存。経験の証明ではない |
| はるちゃんを通して聞いた家族の話 | 家族の話（はるちゃんから聞いた） | 祖母がはるの作るカレーを好きと言った | 家族本人が直接承認した記録と混同しない |
| 誰でも確認できる計算や知識 | 計算・一般知識 | 400g520円は100g当たり130円 | 元の数値・単位を示し、条件変更で再計算 |
| 条件付きの候補 | AIの見込み | 使える材料が残っていたら買い足しが少ないかも | 「もし」「かもしれない」と表現する |
| まだ確かめていない情報 | 要確認 | 今の在庫・何人分・予算・実際の迎え時間 | 不明なら不明。架空の値や家族の合意を補わない |

### 意思決定ログの基本形（設計案）

```json
{
  "situation_id": "dinner-01",
  "utterance": "カレーを作りたい。家庭科で作ったことがある",
  "proposal": "カレーを候補として考える",
  "public_explanation": "作った経験があり、前回は一部の材料があったため",
  "evidence": [
    {"source": "child_report_current", "text": "家庭科で作った経験"},
    {"source": "historical_family_record_demo", "text": "米・玉ねぎ・にんじん・ルーがあった", "freshness": "current_unverified"}
  ],
  "hypotheses": ["まだ残っていれば買い足しを減らせる可能性"],
  "open_questions": ["今日も使えるか", "家族の希望", "人数と予算"],
  "child_choice": "not_decided",
  "child_reason": null,
  "real_world_action": "not_yet_reported",
  "publication_status": "not_shared"
}
```

- UI側で使う「理由」は事実・出所から作る短い説明であり、AIが子どもの心情や未観察の家族会話を創作した文章ではない。
- 説明に使った情報を訂正した時は、提案・比較・記事下書きも再計算／更新する。
- 過去の記録が存在しない家庭には、「以前もあったよね」とは言わない。このデモの前回の家庭調査は**発表用の合成フィクスチャ**として明示する。

## 実践クエスト全13段階での説明

| 段階 | 提案の短い理由 | 本人が次にすること |
|---|---|---|
| 1 献立 | 前回の材料・家族の好み・家庭科の経験などの手がかりを使う（あれば） | 候補を選ぶ／別案／家族に聞く |
| 2 家族の条件 | 人数・予算・手伝ってくれる人で実現できる献立が変わる | 家族に実際に確認 |
| 3 在庫 | 前回の在庫が今もあるとは限らない | 冷蔵庫・棚の現物確認 |
| 4 必要量 | 料理の必要量と家の在庫の差が買い物リストになる | レシピ・箱・家族の希望を確認 |
| 5 価格 | 買う物・量が決まって初めて同条件の価格比較ができる | 2店のチラシ／売り場情報を確認 |
| 6 店の希望 | 価格だけでなく帰る時間・運搬も考える必要がある | 自分の希望と理由を話す |
| 7 頼み方 | 迎えられるかはAIには分からない | 父に何をどこでいつ頼みたいか相談 |
| 8 父の返答 | 迎え時刻と家族の約束で店の選び方が変わる | 本人の案を選び直す |
| 9 決定 | 最安より実行可能性と本人の優先条件で判断する | 理由を話し、父と再合意する |
| 10 店頭の肉 | 100g単価と会計の総額は別の数字 | 必要量を踏まえ量を比較 |
| 11 商品選択 | 割安でも余る・予算超過の可能性がある | 400g／600gなど自分で選ぶ |
| 12 実行 | 予定と実際の購入・調理は別 | 行動して、その結果を報告 |
| 13 新聞 | 選んだ理由を残すと試行錯誤を本人が振り返れる | 本人が文面を確認・修正、共有は任意 |

## 代表的な会話の設計

### 家庭科の経験がある場合
- はる「家庭科でカレーを作ったことがある」
- AI「作った経験があるんだね。前回の記録では米やルーもあったよ。今も残っていればカレーは候補になりそう。**カレーにする？ 別の料理にする？**」
- **未確定**：はるが「カレーを作りたい」と言うまで献立を決めない。

### 祖母の好みを聞いた場合
- はる「おばあちゃんは私の作るカレーが好き」
- AI「おばあちゃんの好みも候補を考える手がかりになるね。前にそう言ってくれたんだね。でも今回何を作るかははるちゃんが決めていいよ」
- **出所**：「はるちゃんから聞いた好み」であり、祖母に直接確認した情報とはしない。

### 前回のにんじん
- AI「前回はにんじんがあった。**今日も残っているなら**使えるかもしれない。見てきてくれる？」
- はる「まだある。4人分使える」
- AI「今回確認できたね。レシピの必要量と比べよう」
- 前回の記録と今回の本人の確認を異なる時点として扱う。

## UI／評価基準

- ひとことの「この提案の理由」は常時表示。詳細の「何を根拠にしたの？」は開閉可能。**AIからの説明文だけで画面を埋めない**。
- 小5でも読める表現（「単価」「予算」のような用語には必要時に補足）。
- サジェストの押下は発言の代行でも決定の承認でもない。必ず本人が選んだときにのみ状態を変える。
- 「違う」「別の料理にしたい」「家族が無理と言った」へ柔軟に戻れること。
- 受入例：前回材料だけで現在在庫を確定しない／家庭科経験や祖母の好みを入力なしで捏造しない／材料確認前に店の比較を始めない／本人の選択理由を新聞で改変しない。
- **単なる説明による納得感は学習効果ではない**。評価は「子どもが説明の根拠を確認できるか」「AI案に反対できるか」「現実で確かめたか」「新しい理由で選び直したか」。
