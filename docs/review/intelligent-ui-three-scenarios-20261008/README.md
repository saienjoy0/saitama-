> 新デモは**子の3体験→私的アルバム保存→母の内容／宛先承認→祖母の日付別新聞と任意の返信・近況→父の実行確認→20P＋40P→50Pカフェ特典予約・承認・提供→次の挑戦**まで、画面で順に試せる合成レビュー用HTML。役割切替は**説明用の見本**であり、実際の認証・権限処理ではない。データはブラウザの一時メモリのみ。通信・実児童入力・本物の音声認識・AI API・実際の金銭移動・祖母への実送信は**行わない**。

## 最短の操作方法

1. **👧 はる**：「①初回」から「このセリフで会話を再現」を4回→アルバムに保存（0P）。次に「②調査」を5回→保存（20Pは父確認待ち）。最後に「③夕飯」を12回→保存（40P確認待ち）。
2. **👩 母**：初回の約束を確認。子が祖母へ見せたい記事を共有依頼した後に、その本文と宛先「祖母」を確認。文章を直したら子へ再確認を戻す。新聞号の発行は任意。
3. **👧 はる**：保存した各アルバムの「祖母にも見せたい」を押す。共有は**まだ未公開**。母が承認して初めて新聞へ表示。
4. **👵 祖母**：許可されたおたよりを読む→「読んだよ」か一言は任意→自分の「元気だよ」を送る。読むだけ／投稿するだけ／返さないも成立。
5. **👨 父**：調査20Pと夕飯40Pの実行申告を別々に確認。一度だけ計60P確定。**新聞への共有と無関係**。
6. **👧 はる**：家庭登録されたカフェ50Pを依頼→利用可能10P、50P予約中。
7. **👨 父**：交換を承認してもカフェは未実施。実際に体験した（合成）操作の後だけ「提供済み」。提供不能なら返還。
8. **👧 はる**：祖母の返信・過去の記録を見て、次を選ぶ（強制しない）。

実際の画面では操作順は固定進級ではありません。上記は導線検証用の推奨一周例です。**前の [presentation.html](./presentation.html) は3シナリオの子の声と画面生成演出の旧レビュー見本**で、母・父・祖母・報酬の一周を含みません。

## 修正の要点と結果

- 買い物リスト（肉400g、じゃがいも1袋、トマト2個）が決まる**前に店の価格を出さない**。
- 家族の条件を本人の報告と区別。予算・迎え・祖母の好み／家庭科の経験を勝手に発明しない。
- 本人の非公開保存、祖母への共有希望、母の内容と宛先承認、実際の公開を分ける。
- 新聞号と日付別の閲覧を区別し、母に毎日編集作業を要求しない。
- 父の活動確認（報酬の確定）と母の共有確認を切り離す。
- 祖母は読んで終わりではなく、自分の歩数（一言として**手入力**）や近況を送ることができる。
- 本人の報告で実際の行動が証明されたと装わず、金銭残高・共有・新聞・受取を状態分離する。

## 2026-10-08：実機スクリーンショットを受けた緊急レイアウト修正

**確認できた問題**：Androidの実画面では、従来の大きい下部固定入力パネルがAIの返答とその下のカードの上に重なり、カードの最下部まで見られなかった。「スクロールできるはず」という設計だけでは使えないことが画像から確認された。

**修正した構造**：生成された会話／カードをスクロールする部分と、マイク・入力を使う下部ドックを**DOM上で兄弟要素の独立行**にした。ドックは画面の高さから領域を確保するので、スクロール中のカードの上へ重ならない。

- 入力の高さを抑え、**文字入力・🎙マイク・➤送信を1行**にした。次のセリフの候補は細い横スクロールのチップにする。重複した見出し・大きな送信ボタン・通常の処理完了ステータスを除き、返答の視認領域を確保。
- 画面の可視高を `visualViewport.height` から更新し、スマホのソフトキーボード出現時にドックが表示領域から落ちにくい構造にした。Androidの入力中の実機確認は未実施。
- 発話後は最新の会話に自動スクロール。**カードの全内容はドックと重ならず、上部の閲覧領域内でスクロールして読める**。実機での見切れは未検証。
- 実画面にあった「材料を確かめてきた」に対し、**材料名をまだ聞いていないのにA/B店の価格へ進んでしまう問題**も修正。「冷蔵庫に何があった？」と聞き、確認前に価格を表示しない。
- 店の値段と迎えの時刻が未報告なら「未確認」。報告されていない4人分や1,000円、16:45の帰宅約束も事実のように表示しない。台本を再生成し文言との対応を維持。

**確認**：最新版HTMLを読み戻したJavaScript構文＋模擬DOMで26項目PASS（下部ドックのDOM上の独立、固定重なりのCSS解除、可視高変更、台詞に対する模擬応答、未確認データを作らないこと、3シナリオの基本継続）。**実際のスマートフォンの表示・マイク・キーボード・タッチ操作はまだ再試験していない**。以下リンクは表示を保証するものではなく試用用。

## 2026-10-08：最初の問いをクエスト別に変更

**問題**：「今日は何をやってみたい？」「何から始める？」は、初めて使う小学5年生に課題の発見・手順まで考えさせる。クエスト自体が選ばれた状態なら、アプリが最初の具体的な問いを渡した方がよい。これは製品効果の実証ではなく、子が最初の操作を理解しやすくするための設計判断。

| クエスト | 初期タイトル | AIの最初の問い | 期待する最初の返答 |
|---|---|---|---|
| 実践・夕飯 | おばあちゃんと食べる夕飯を考えよう | 今度のおばあちゃんとの夕飯、何を作ってみたい？ | 「カレーを作りたい」 |
| 初回の約束 | 夕飯のこと、どこまで自分でやってみたい？ | 献立を決めることと買い物、どっちを自分でやってみたい？ | 「献立を自分で決めたい」 |
| 調査 | 夕飯の前にある仕事を探そう | 料理以外にどんな準備があると思う？ | 「買い物に行くこと」 |

- **最初の質問を模擬AIが先に示す**。子の最初の発言を勝手に作らず、最初のカードにはクエストに合う具体的な問いだけを表示する。
- 「まだ決まっていない」「分からない」ならその場で一歩だけ補助する。最初から詳細な予算や家族の条件を要求しない。
- 数字を話していない場合は、人数や予算の条件欄を「家族に確認」「家族と相談」と表示する。以前の合成例の数字を本人が言ったこととして表示しない。
- 3シナリオ14ターンの返答台本は実際の模擬UIの内容に合わせて更新。発表用合成例と実際の子どもの行動を明確に分ける。
- 参照：PR #11 の子どもの1画面1判断・16px本文・48px操作ルール、PR #12 の行動起点と必要時にだけ音声で話す原則、main の REFERENCE_BEFORE_CHANGE.md。


## 何を見せるか

主役は小学5年生のはるちゃん。発表者がページをスクロールして見せる仕掛けよりも、子どもがスマホで使い続けられる導線を優先する。

1. 最初の画面で「🏠 初回の約束」「🔎 調査クエスト」「🍛 実践クエスト」を選ぶ。「クエスト」「やりたいこと」「最初のサジェスト」「声／文字の入力」だけを見せる。価格比較などのカードはまだ出さない。
2. 画面下部にあるマイクを押して話す。対応ブラウザーなら音声認識で文字化する。非対応・拒否の場合は同じ場所に文字入力。
3. 「はるちゃんが話した言葉」→「模擬AIの返答」→「今の情報から組み立てられたカード」が順に現れる。
4. はるちゃんが家族に聞く／家の食材を見る／値段を調べるなど現実の行動をし、戻って新しい情報を話す。実行や合意をAIが代行・確認したと見なさない。
5. **ここから上に戻る必要がない**：幅740px以下でアプリを画面の高さいっぱいにし、会話とカードを読む領域と、画面下部の小さな入力ドックを独立して配置。下部ドックはカードを覆わない。新しい会話に自動スクロールし、次の発言候補は小さなチップで表示する。
6. 「わからない」とだけ話しても、その直前の話題についてヒントを返し、最初のメニューに巻き戻さない。実行を報告したら本人の発言から新聞の下書きを表示する。本人が言っていない経験は創作しない。

## 発表用の具体的操作

- 端末で開くと、最初に子どものクエストとマイクが見える。「カレーを作りたい。4人分で、予算は1,000円」と話す。
- AI風の返答と行動のステップが現れたら、はるちゃん役が冷蔵庫を見る。戻って「家に米とルーがある」と話す。マイクは画面下部に残っている。
- さらに値段を調べ、家族に迎え時間を聞く。戻るたびに、**同じ位置のマイク**を押せば続きを話せる。画面を上にスクロールする必要がない。
- 上部の「📚 クエスト ▾」からいつでも別のクエストへ切替可能。発表者用の台本・再生は小さな「⚙」から別パネルを開く。客席には基本的に子どものアプリだけを見せる。
- 端末にマイクがなければ文字入力。任意のサジェストを選んでも未送信のまま。本人が書き直して「AIに相談する」を押した時だけ発言として記録する。
